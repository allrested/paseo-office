# Office 3D guide

Open **Office 3D** from the Paseo sidebar to see the host’s workspaces and agents. **Open office** in the Command Center opens a tab with the current workspace’s room first. Agents without a workspace appear in the lobby.

## Work in fullscreen

1. Choose **3D** and **Full screen**. **Sessions** on the left shows who is working, resting or waiting for you. **Details** on the right shows activity or the selected conversation. Toggle either sidebar in the header to give the floor more room. [Office with both sidebars](fullscreen-office.png) · [Floor with both sidebars hidden](fullscreen-floor.png)
2. Select a session row to read its conversation. Click the **↗** beside the row to open the agent’s full Paseo workspace over the floor. In **Walk in**, press **E** at an agent’s desk for the same workspace. The minimize button keeps it available from the camera toolbar. Closing it returns you to the floor. [Embedded workbench](fullscreen-workspace.webp)
3. Inside the workspace dialog, choose **Office controls** for the conversation, steps and subagents. A reply can join the running turn. **Workspace** switches back to the embedded workbench. On clients without an embeddable workbench, Office shows the session controls directly. [Desktop controls](workspace-controls.webp) · [Controls at phone width](workspace-controls-mobile.webp)
4. Choose **Team chat** in the header for the shared conversation. Address a session through **To** when you want it to take an action. An assignment that should remain visible until completion belongs on the lobby board. [Floating team chat](fullscreen-team-chat.webp)

For configuration, see [Office settings](#settings), [branding](#custom-branding), [boards and wakes](#boards-and-wakes) and the [duty board](#the-duty-board). The port’s upstream revision and asset credits are recorded in [the vendor sources](../vendor/SOURCES.md).

Server code cannot import from `client/`, and client code cannot import from `server/`, even for a
type: the plugin compiler refuses both. Shapes both sides use live in `shared/`. The plugin bundle
has no platform file extensions (`.web.ts`, `.native.ts`), so `client/office-surface.tsx` picks a
view by `layout.platform`.

The host supplies `@getpaseo/plugin` and `zod` to an installed plugin, and esbuild bundles
everything else from this folder when the plugin is installed. So the plugin has no runtime
dependency beyond those two, and installing it runs no build. A new dependency would need a `build`
step in the manifest.

## The directory

The server keeps one directory of agents and workspaces from subscribed `agents.list` and
`workspaces.list` calls (the first 200 of each) and streams a compact projection over the
`office.state` subscription. The directory and the 5 s "doing now" reads run only while an office
surface is open.

A row shows the agent's state, provider and model, and for a running agent a "doing now" line taken
from the newest timeline item's kind, never its text. When that item is a tool call, the same read
gives the agent's step: the kind of work (a read, a search, a skill, an edit, a command, a test run,
a commit, a push, a deploy), the call's id, and for a test run or a deploy how it ended. The server
decides the kind from the tool call's normalised detail, and for a shell call from its command
(`server/activity.ts`); the command, a file name or a query never leave it. A deploy is a tool
named for one (`deploy_service`), a deploy script or a `make`/`just` target, a Dokploy redeploy, a
run of a deploy or release workflow, a push of a version tag, or a hosting tool's own command. Run
as a check or a dry run (`--check`, `--dry-run`, `--list`, or `-n` to make, just or a deploy
script), it is a command.

The reads are 5 s apart. A tool call that starts and ends between two of them, as a web search
often does, is the step of the read after it, for that one read.

A provider can also run sub-agents inside an agent's own session, as Claude's Agent tool does.
Those are no Paseo agents: they have no session, no card and no row. The office finds them in
the agent's timeline, as `Task` or `Agent` calls that still run, at its 5 s reads, and the 3D
floor draws each one as upstream draws a sub-agent: it comes in through the door, takes its brief
from the agent that started it, works, reports back when its call ends, and leaves. Its name is
the kind of sub-agent the provider gives ("Explore"), never its task. A call that starts and ends
between two reads is not seen, and a call older than the tail the office reads is missed. The 2D
floor and the lists do not show them.

An agent whose own turn has ended is not idle while an agent it started, or one those started,
runs, starts or waits for you: it waits on them. `waitingOnOf` in `shared/model.ts` is the one
place the rule is worked out. On both floors such an agent stays at its desk, at work; the
whiteboard and the stand-up say "Waiting on N sub-agents"; and the stand-up, the Library and
Review cards and the janitor leave it alone. Only agents the office shows count. The stand-up
report for the notes writer follows the rule too, but the server's wakes and clean-ups do not:
they take such an agent for idle, so a mention on a board wakes it, and the Host card can still
close a waiting agent.

## Agents at home

Paseo closes the runtime of a session that has been idle for a while. The session is still there,
unarchived, and its next prompt starts it again: the office takes such an agent to be at home. It
has no desk on either floor and is in no room's rows, so the boards, the stand-up and the Janitor
leave it alone; the Sessions list keeps it, in an **At home** section under Resting,
and counts it in All and Resting. Selecting it opens its conversation, and a reply brings it back.

A task brings it back too. The lobby's to-dos and the duties with instructions go to the idle
agents first; when none is free, the agents at home are next, the one that left last first, so a
task no longer waits for somebody to finish. A post that names an agent at home wakes it as it
wakes an idle one. An agent at home keeps the tasks and duties it claimed, and a question it asked
with `block`: they are freed only when it is archived, and until then the Tasks card lists them
(see Boards and wakes). The team chat's whole-group messages do not: only work calls an agent back.
An archived session is gone from the office, as before, and so is a sub-agent that closed.

## The agent card

Tapping a row, a desk or a person opens the agent's card. It opens the session, sends a prompt,
and answers a tool, mode or other permission. A plan or a question is not answered on the card:
it says "Answer in the session", and the card's own "Open session" is the way there. A row of the
List or an Activity card puts an "Open session" button beside it instead. Stop ends the running
turn, and is offered only on a host whose SDK has an agent's
`cancel()` (`shared/host-extras.ts`); stock Paseo 0.16 does not.

"Open session" shows the session in the office's column (see below) in every app, and the card
closes as it does. In walk-in mode, face an agent and press **E** or tap the on-screen prompt to open their workspace. The same action wakes a sleeping character. **Open in workspace** also opens the selected session’s Paseo workbench over the office. In the browser it uses the paired host’s own workspace, including files, diffs, terminals and session tools. **Office controls** offers session replies, permissions and the room board on native clients and when the workspace cannot be embedded. Closing the overlay returns to the same floor and camera.

## Team names

A room is a workspace and goes by the workspace's name, which is often a branch or a ticket.
"Rename team", under a room's title in the List view and at the top of a room's board in every
view, gives the team a name of the office's own, at most 40 characters. It is kept on the workspace in the plugin's data (`office.team.name`), so
it needs a host that keeps plugin data on workspaces, and every device sees it. The office shows
it wherever it showed the workspace's name: the room and its board, the session lists, the
stand-up and its notes, the team chat and the 3D floor. The workspace keeps its own name in Paseo,
and the room's card says which workspace it is. An empty name goes back to the workspace's.

The 3D floor remembers where a team sat by its name, so a renamed team is seated as a new one.

## Team roster

Settings > Office 3D > **Teams** holds a roster: teams, in the order they
are filled, each with its teammates. With "Name teams and agents from the roster" on, the office names by itself:

- a team is its teammates, whatever workspace each agent works in. Agents, sub-agents too,
  oldest first, each take a teammate of the first team that has one free, picked by chance
  among that team's free ones. So the first team fills before the second;
- on the 3D floor a teammate sits with its team: one desk area per roster team, not one per
  workspace;
- an agent the roster has nobody left for keeps the name it has today and sits with its
  workspace's team. A sub-agent is then `<parent's name>-<number>`, and the parent's name can
  be a teammate's;
- a closed agent is handed nothing. One that holds a teammate keeps it until it is archived.

A name sticks until its agent is archived. A freed teammate goes to the next new agent; nothing
that already runs is renamed. Adding a team or a teammate, or switching the roster on, offers
the longer list to the agents that were passed over before.

The names are the office's own: Paseo's sidebar, tabs and CLI show the workspace and session
names they always did, and so do the office's lists and boards, which stay one room per
workspace. A name you type on an agent wins over the roster, and a team name you type on a
workspace keeps that workspace's agents together under it on the floor. Renaming a team or
teammate in the settings renames whoever holds it; removing a teammate leaves its holder with
today's name until the roster next grows, when it is offered a name again. Switching the roster
off shows today's names everywhere, and on again brings the same assignments back and looks once
more at what was passed over.

What is stored: `office.roster.member` on an agent, the id of the teammate held, or a number
when the roster had nobody left for it. Up to 0.2.13 a team went to a workspace and
`office.roster.team` was stored there; it is no longer read or written. Where 0.2.13 gave one
teammate to agents of two workspaces, the oldest keeps it and the other is named again.

A lobby task can be given to a team, from the lobby's form or `office_post`: only its teammates'
agents are handed it (see Boards and wakes).

## Views

The office has three views: a 3D floor, a 2D floor and the list. A switch over the floor's top
right corner chooses one per device and keeps it in the `office-device` setting; the office's
settings screen has the same switch. Over the list the switch takes a row of its own.

A device that never chose shows the 3D floor where it can draw it, and the 2D floor anywhere else:

| Where                         | 3D floor | 2D floor | List |
| ----------------------------- | -------- | -------- | ---- |
| Desktop app, browser (WebGL2) | yes      | yes      | yes  |
| Phone app with `ScriptFrame`  | yes      | yes      | yes  |
| Store phone app               | no       | yes      | yes  |

On the web and in the desktop app the scene runs in an `iframe` of its own
(`client/world/world-frame.web.ts`). In a phone app it needs the plugin kit's `ScriptFrame`, a
frame that runs a script (`client/world/script-frame-kit.ts`); `client/world/world-bridge.ts`
carries the scene's API over messages. The store app's plugin frame runs no script, so it gets the
2D floor and the list. An app's page finds out whether the phone has WebGL2; with none, and for
any other failure, the 3D floor gives way to the 2D one under a banner with a way to try again.
Photo mode is off in an app, since a WebView cannot keep a download, and so are clips. The tour is
off wherever the screen is touch.

The list's bar filters the room cards by tab (All, Needs you, Working, Resting) and by a search
that `/` focuses on the web. Each row adds its context, its turn's clock or how long it has
rested, and its cost (`client/list-text.ts`).

In browsers that support fullscreen, the Full screen button beside the view switch expands the
office. Wide screens show Sessions on the left, the floor in the center, and Activity or an open conversation on the right. **Team chat** opens a floating messenger over the floor. Select an agent to read the conversation, reply, or answer a
permission request. Use **Sessions** and **Details** in the top bar to hide either sidebar or both.
The device remembers your choice. Restoring Sessions brings back its search and filter, and
restoring Details brings back the conversation and reply draft. Narrow screens open these panels
as sheets. Exit full screen or
press Escape to return to Paseo.

## The column

The office draws its own column beside the floor (`client/office-column.tsx`), with Attention,
Sessions, Activity and Chat tabs. Only the chosen tab's panel is mounted, and only the chosen tab
shows its label: four labels do not fit the narrowest column, 280 px. A drag handle sets the width
(280 to 560, 360 by default; the floor keeps 320), and a button collapses the column to a rail of
the tabs. On a compact layout the floor fills the page, a bar of the tabs sits under it, and a tab
opens the column as a sheet over the floor (`client/column-sheet.tsx`); Close, a press above the
sheet and Escape close it. Width and collapsed are the `office-column` device setting, kept apart
from `office-device` because that one is saved whole.

An open session is a tab after the four, with the agent's status dot and title and a button to
close it (`client/session-panel.tsx`, `client/use-conversation.ts`). Tabs past the column's edge
scroll sideways: with a mouse the scroll bar shows, and the tab of the session just shown is
scrolled into view. Chat shows formatted replies and folds consecutive tool calls into an
expandable row. Failed and canceled calls stay visible. **Steps** lists each tool call individually.
A lobby assignment shows the task and expands to reveal the original instructions.
The session also shows requests with Approve and Deny, a reply box, and Stop while
a turn runs on a host that can stop one. A reply joins the running turn (it does not interrupt
it); while a request waits, the daemon denies that request when the reply goes in, and the box
says so. On the web the reply box has an **Attach images** button, the chat's own: up to four
images, each resized to a JPEG before it is sent, and they go with the reply, a running turn
included. Images alone are a reply too, and say how many. A native client shows no
button. The host's prompt call takes images but no file, and a plugin cannot upload one, so the
**Attach text files** button beside it adds a text file's text to the message instead: up to four
files and 100 KB together, each under a header naming it (`--- Attached file: name ---`, then the
text, then `--- End of name ---`) after what was typed, and a chip shows its name and size with
a Remove and says the text is added. A file that holds a NUL byte or is not UTF-8 text is
refused. A PDF, an archive or any other binary stays a job for **Open in workspace**. What is half typed in a reply box is the surface's, by agent, as the Chat box is: a
tab switch or a dismissed sheet keeps it, the attached images and text files with it, and a sent reply or a
closed tab clears them; a reply that fails to send keeps them. A plan or a question is answered in the session too (`client/ask-card.tsx`, `client/ask-form.ts`):
a plan shows its text with the request's own actions, or Approve plan and Keep planning, and a
line of what to change that goes with a refusal; a question shows its form, the options as
buttons and a box where another answer is taken, with Send answers once each question has one,
and Dismiss. The office reads the request from Paseo when the session shows it; a request it
cannot read, or of a shape it does not know, says to answer it in the workspace. Typing `/` in the reply box lists the slash commands and skills the running session reports
(`client/session-extras.ts`): the list narrows as the word is typed, and a press puts the command
in the box with a space after it for what it takes. It is read from Paseo the first time a slash
is typed, and a command can be typed whole and sent where there is no list. **Options**, over the
box, shows the session's own options as its provider describes them to Paseo, each a switch or a
row of choices, and a press changes one at once; what a provider refuses to change says why. That
is how a model or a mode is changed here, for a provider that offers it as an option: Paseo gives
a plugin no call of its own for either, so a provider that offers neither shows "This session has
no options to change here." For other files or terminal work, choose **Open in workspace**. A session that leaves the directory keeps its tab until you close it. On a compact layout the sheet shows the session with a Back to Sessions button;
dismissing the sheet leaves the session open, and the Sessions tab on the bar carries the count.
The open sessions are kept on the device (`sessions` in the `office-column` setting, twelve at most), so a reload opens their tabs again, on the Sessions tab; the chosen tab itself is not kept.

## The 3D floor

The scene is [my-office](https://github.com/khanh020905/my-office), vendored under
`vendor/my-office/`. An installed plugin is not told where its files are: the daemon compiles its
server into one bundle. So `scripts/build-world.mjs` bundles the vendored entry into
`server/world.generated.ts`, as one string, and the server serves it through
`office.world.request`. The module is committed. `npm run check:world` fails when the committed
module is not what the build makes, so run `npm run build:world` after any change under
`vendor/`.

The client runs the script in a frame and drives it through the `PaseoOfficeWorld` object it sets
(`client/world/world-api.ts`), mapping the office model to the scene's people in
`client/world/adapter.ts`. The scene is one app per page: module state, a stylesheet for `html`
and `body`, listeners on its window. The frame keeps that out of the app's page, and removing the
frame ends it. Keys pressed inside a frame do not reach the app's shortcuts, so a press on the
scene, and anything the scene opens in the app (the agent card, a board), gives keyboard focus back
to the app's window.

The scene is told who is there and what kind of thing each does, and the open incidents' keys and
titles for the banner. It receives its language, its dictionary and the daily-life data described below, without file names, commands or prompts. It makes no network call. It
writes scene state to the app origin's `localStorage` under keys that start with `office-`:
which team sits where, the plants, the graphics level, the Sound switch (`office-sound`, which
the host's setting overwrites at each start), that the tour was seen (`office-tips`), and the
clip's shape and music choice (`office-clip-shape`, `office-clip-music`), the cups in the pantry's sink (`office-duty`), drill and farewell history. It reads
`office-autocam`.

The shops, apps and products the scene's text and the team chat name (the cafés and stores people
pop out to, the ride and delivery apps, the bank, the medicines) are made-up ones, not my-office's
real brands. `scripts/street-brands.mjs` lists each real name with the one it becomes, and
`scripts/genericise-street.mjs` swaps them in every vendored file; its `--check` and a test over
the bundle fail on a real name left.

An agent is a person at a desk, and a workspace's agents sit together as a team. The company floor
has 12 desks, the cozy room 9, and Headquarters 44. Headquarters adds four eight-desk rooms beyond the main floor. Each room’s plaque shows the workspace seated there. With more agents, the ones that need you and the ones at work sit
first, and a line over the scene says how many are only in the list.

The host setting "Floor plan" stores `pro`, `cozy` or `hq`. The company floor is the default. The surface reads it (`client/world/use-floor-plan.ts`) and hands it to
the 3D view. A change unmounts the scene and mounts a new one, because a scene page starts once.
The setting is for the 3D floor only: the 2D floor and the List do not change. The cozy room is
one open room. It has no lobby and sign, no director (he still talks in the team chat), no screen in
its meeting corner and so no "Stand-up notes" label, no lounge with its games and sofa, no restroom
and no dining room. An agent at rest there goes to the fish or the arcade. The camera bar's four
views look at that plan's places. In Headquarters the Desks view looks into the wing.

A step sends its person to that work's place: the library for a read, a search or a skill, the
desk for an edit, the server room for a command, the test board for a test run. A commit prints a
page, and the desks near a push applaud, once in ten minutes a person. A deploy is a command at the
server room's console until it ends: one that succeeds launches the rocket and is applauded every
time, one that fails gets the failure's sweat, and one cancelled or never seen to end does nothing.

With a host reading, the server room's chip, its racks and the wall screen open the Host card, the
wall screen shows memory and CPU, an agent with a port open has a small server on its desk, and
what was left running stands in the server room under a red light. On an app with a side area, the
wall screen opens a Resources screen beside the floor instead, when the host has one. The paper on
a desk and in its bin is the agent's context, with a flag in it from 85%. When a context falls to
less than half of what it was, by a compaction or a new conversation, the person carries the paper
to the shredder.

The camera moves by itself for one thing: a person already in the office whose status becomes
"waiting for you" has the camera glide to them for 7 seconds, then back. Not while the camera was
moved in the last 30 seconds, someone walks the floor, a photo is taken or a card is open, and
anything else that takes the camera (a view, a zoom, a drag) ends the glide. It is on by default.
There is no setting for it: the `localStorage` key `office-autocam` set to `off` turns it off.

Photo mode's bar holds the light for a photo: Auto follows the app's theme, Day and Night hold
against it, and leaving photo mode puts the lights back. A theme change that reaches the scene
lets go too; stock Paseo's web app starts the plugin's whole screen again on a theme change, so
there the scene simply starts in the new theme (see [verified.md](verified.md)). The wall clock
does not change the lights, and its tooltip says so.

On a desktop's first visit to the 3D floor a tour shows: six or seven cards, each over the thing
it is about (the lamp, the switch, the coffee machine, the printer, the cat, a person, Walk in),
skipping what a floor plan lacks. It shows once per device (`office-tips`; remove the key to see
it again), ends at Skip, Done, Escape, Walk in or Photo mode, and never shows on a touch screen.

Photo mode's bar also records a clip: "Clip 15 s", in a square or a vertical shape, with Music.
It is offered on a desktop or in a browser that has a recorder, never on a touch device and never
where Photo mode is off. The clip is made in the page and saved as a download named
`office-clip-...`; nothing is sent anywhere. The music is made in the page too, goes into the
recording and not to the speakers, and is made only while Sound is on: with Sound off the Music
button is dimmed and the clip is silent. Escape and P do nothing while a clip is made; its own
Stop ends it and saves nothing. What a clip shows is the scene's own: the floor, the people's
names and counts of prompts, edits, commands and deploys, never a file name, a command or a
prompt.

Opening the stand-up rings the bell on the meeting table: everyone the scene counts as free walks
there and says what they are on. A click on the bell does the same and also starts the stand-up
notes writer; opening the stand-up writes nothing. Click or tap the meeting room’s **Sprint review** screen to read the stand-up notes. Its **Stand-up notes** label also opens the reader from the keyboard.

From 08:00 to 21:00 by the device's clock an agent at rest does not stay asleep at its desk: after
30 to 90 seconds there it gets up for a game of pool, foosball or the games TV with another resting
agent, for karaoke, a nap on the sofa, the fish, the arcade, a cup in the dining room or the
restroom, never the same thing twice running, and work calls it back at once. After two hours of
rest the gaps are 10 to 20 minutes. The games are my-office's; the office's plan
(`vendor/my-office/src/office/paseo-leisure.js`) only starts them, and starts nothing at night,
during a gathering or with reduced motion. After 21:00 an agent that has rested 30 minutes walks
home, its rest counted from the host's last change of the agent.

By default, heading home only affects the scene. Turn on **Office settings → Automation → Archive idle sessions** to archive an eligible idle agent’s Paseo session when it heads home at the end of its shift. Sessions with a pending approval or a working subagent stay active.
An agent out for evening drinks can still return to work. With the setting enabled, Office archives its still-idle session when it finishes the trip home.
Archived conversations keep their history and stay off the floor when Office reopens.

The viewing device’s date selects decorations when the scene starts. Halloween runs from 20 October through 1 November, Christmas from 12 through 31 December, and Lunar New Year from 14 days before through seven days after its date in Vietnam’s calendar. The upstream table covers 2026 through 2033. These dates apply in both hemispheres.

### Languages

The device setting `office-language` chooses Automatic, English, Tiếng Việt, ไทย or Bahasa
Indonesia. Automatic takes the app locale’s primary language subtag (including legacy `in` for
Indonesian) and falls back to English. The scene bundles English. For another language the
client requests one JSON text from `office.world.words`, backed by `server/words.generated.ts`,
and caches the successful response. The scene waits for the words before drawing labels. A change
of language starts a fresh frame. A failed download leaves the floor in English with a note.

The lookup checks the chosen language’s port overrides, the English port overrides, the chosen
dictionary and finally the English dictionary. It removes decorative emoji and preserves lines
made entirely of emoji. The column, chat, settings, whiteboard and host messages keep their
existing text. Vietnamese has its own karaoke lyrics. Thai and Indonesian use English lyrics.

### The interface's language

The office's own interface follows the same choice (`client/ui-language.tsx`): with Tiếng Việt,
ไทย or Bahasa Indonesia chosen, or Automatic in an app whose language is one of them, it is in that
language; with English, or any other language, in English. That covers the buttons, the fields with their hints
and placeholders, the switches, the dialogs and what they say, the column, the cards, the
settings page, and the lines put together from data: an age ("12 mnt lalu"), a count, an agent's
activity, the cards' summaries, a failure up to the host's own reason.

Every view draws its words through one text component and one text field (`client/text.tsx`).
A text that is one string is looked up whole in the language's table (`shared/ui-words-id.ts`,
`-vi.ts` or `-th.ts`), by the English it stands for, and then against the shapes in
`shared/ui-patterns-id.ts` (`-vi`, `-th`), which carry the data over as it is. Vietnamese and Thai
have no plural, so a count is the number and a classifier ("3 tệp", "3 ไฟล์"). The three tables
have the same keys and the three lists of shapes the same shapes in the same order;
`shared/ui-languages.test.ts` fails when a text or a shape is in one language and not in another. A text with no entry and no shape is shown in English. What a person or an agent wrote goes
through the same component, so a shape takes a line only by words no title is likely to end in.

Not translated: the reason a host or a provider gives for a failure, a name read out by a screen
reader where it is put together from several parts, host notifications and the webhook's
message, and the prompts the office sends to agents, which stay English for the agents' sake.
The people in the team chat speak by the host's **Team chat** setting, which has Indonesia of its
own. The Vietnamese and Thai interface was written by a machine and has not been read by a
native speaker (see `docs/verified.md`).

### Sound

The scene's sounds are my-office's, made in the page with Web Audio, no sound file: all of them
but one shop's tune. They are off until turned on. The switch is the `sound` field of the
`office-device` setting (off by default), so it is the device's, not the host's: the settings page's
"Sound" switch and the speaker button on the floor's toolbar, after Photo mode, both change it.
The host sends the switch to the scene with `setSound`; the button asks for a change with
`onSound`, and the host stores it and answers with `setSound`. The page starts off.

A browser lets a page start audio only inside a press, so the scene's audio starts there: a press on
the button plays at once, and a press anywhere in the scene starts the audio the switch turned on. A
probe (`paseo-sound.js`) finds out whether the frame allows audio at all. It runs inside a real
press only (not for Escape or a bare modifier key, and not while the page has no user activation),
and makes and closes a context of its own. A page with no Web Audio is "not available" at once, for
good: the button's icon is dimmed, it says "Sound is not available here", and a press on it shows
the note "This app does not let the office play sound." and changes nothing. A press after which no
context ran makes the button the same, and holds the scene's sound off without changing the setting;
the next press tries again. Once a context runs the button can be used again and the scene follows
the setting with no further press: on if the setting is on. A press on the button itself while audio
is held off waits for the probe that press started: if audio then starts, the press turns sound on
as any press on it does; if not, it says "This app does not let the office play sound." A press on
the button means what the button showed when the press arrived: the probe that press starts may
turn the scene's sound on before the button hears of the press, and the press must not then turn it
off again. The speaker's drawing takes no presses itself, so a press on it is a press on the button
even when the probe redraws it meanwhile. The scene shows such a line itself, on the floor and not
as a toast of the app: a note over the floor's toolbar, read out politely by a screen reader, for
four seconds, a new one replacing it. The games and karaoke show their lines the same way.

A Sound save the device refuses is said where the switch was used: under the settings page's
switches, or in the floor's view corner, where the view switch's own refusal shows (that one first
when both are refused): "Unable to save the Sound setting on this device. It holds until this
screen is closed."

Karaoke follows the switch, because it reads `sfx.on`, and so does the incidents' siren. Every
saver of the device's document (the view, the incidents rung, the Sound switch) writes it whole,
so changing one keeps the others.

## The 2D floor

The 2D floor (`client/pixel/`) is pixel art drawn with plain views, one per rectangle of colour.
Plugin code in the app has React Native views only, with no canvas and no SVG, and a scaled image
is smoothed there, so views are the one way to get sharp pixels on every platform. The floor needs
nothing from the host beyond `office.state` and `office.machine`, so it is also what a slow machine
can choose. A picture is a grid of letters in `client/pixel/art.ts`, compiled to rectangles once
per theme tone. One art pixel is a whole number of screen pixels, 2 on a phone and up to 4 on a
wide surface; the room is as wide as the surface and scrolls down, never sideways. It has 40 desks:
more would make a phone lay out thousands more views, and the line under the room says how many
agents are only in the list.

The places are the 3D floor's: the library for a read, a search or a skill, the racks for a command
or a test run, the whiteboard for a plan or a sub-agent, the desk for a push, the racks for a deploy
that runs, the pad for a deploy that succeeded, where the rocket flies, and the desk for everything
else. Whoever needs you stays at the desk, where a tap opens the card. Where a person stands follows
from the agent's state (`client/pixel/actors.ts`), and the lounge's turn also from the time, so an
office opened in the middle of a turn shows everyone in place.

Three things are remembered: the coffee break, 30 seconds away from the desk after a turn ends;
since when each agent rests; and the desks the janitor is due at. While the stand-up is open,
whoever rests stands at the whiteboard. From 08:00 to 21:00 by the device's clock whoever rests
takes turns of three minutes in the lounge, on the sofa, at the coffee machine or at the plant, and
at the desk between them; an agent that has rested two hours goes one turn in six. The turn follows
from the agent's id and the time (`restWishes`), so every device shows the same floor.

A desk opens its agent's card, a team's plate and the whiteboard open a board, and the racks open
the Host card. A person away from the desk can be tapped too, but only the desk is a stop for the
keyboard and a screen reader, and it says what its agent is at. A janitor stands by a cart in the
lounge, and the two open the Janitor card; when a context empties, the janitor walks to that desk
and sweeps. With reduced motion nobody walks, nobody takes a break or goes to the stand-up or the
lounge, and the janitor stays at the cart.

The 2D floor seats the teams the 3D floor seats (`client/pixel/teams.ts`): a room, or with the
roster on a roster team, whose teammates may work in several rooms; such a team's plate opens the
board of its first member's room. While an incident is open a red banner over the floor names the
newest and how many more are open, and a press opens the Incidents card: the 2D floor's alarm,
with no light and no siren. A desk whose agent has the provider's own sub-agents at work shows
their icon until a step says more, and its name says how many.

## Boards and wakes

Each room has a board, and the lobby has one for the host: posts are tasks (open, claimed, done) or
notes, kept in `<PASEO_HOME>/office/boards.json` (200 per board, done tasks dropped after 7 days).
The lobby's to-do list defaults to **Any idle agent**. An available interactive session picks up
each open task and appears on the board as its claimant. The claim stays until the task is marked
done or reopened, or until its agent is archived, which reopens every task it still held
(a lobby task with its copy included) for the next idle agent. A session Paseo has closed is at
home (see Agents at home), not gone: it keeps its claims and what it asked for, and the Tasks card
lists them. Choose a specific agent to send it the task when idle. Turning off **Wake agents**
pauses both automatic pickup and named wakes. Automatic pickup also requires **Agent tools** so the recipient can finish the task on the board. Open tasks stay on the board between host restarts.
A session whose board tools became unavailable after a reload can finish its own assignment using the exact completion line in its prompt. Other replies keep the task claimed. **Clear finished** deletes completed to-dos.
The line names the assignment's number ("assignment 12"), which the task keeps from the moment it
is handed out: a block, its answer and a reply change the task and leave the number, so the line
still finishes it after them. A reopened task loses the number and gets a new one when it is
handed out again.

The lobby's board is a kanban: its to-dos and notes in columns, **Backlog** (held), **Waiting**,
**To do** (open), **In progress** (claimed), **Needs you** (claimed and blocked), **Done** and
**Notes**. To do and In progress are always there; the others show only when they hold something. Each heading says how
many the column holds, as in "To do · 3". A task is a card with the list's checkbox and delete
button, and a note keeps its Delete button. A card changes column through those buttons; nothing
is dragged. **Clear finished** is in Done's heading.
When the board is 720 px wide or more, the columns sit side by side, 280 px each, and scroll
sideways when they do not fit; in fullscreen a kanban's board opens in the wide dialog to make
room for them. Narrower, as on a phone, they are stacked sections: a press on a heading folds or
unfolds its section, and Backlog and Done start folded. The form stays above the columns and **Agent tasks**
under them.

**Boards** in the settings chooses each board's layout on this device: **Lobby board** Kanban (the
default) or List, and **Room boards** List (the default) or Kanban. A room's board as a kanban has
the same columns under its form and its agents, Done included. The list is the board as it was:
the lobby's to-do list with its notes under it, and a room's posts in one list. A room's list keeps
its finished tasks in a **Done** section at the bottom, shown once a task is done: its heading says
how many, as in "Done · 2", starts folded and unfolds with a press, and has **Clear finished**
beside it. A room's card still shows and counts only open and claimed tasks and notes.

A lobby task can be held in the **Backlog**: it stays open but is not handed out, and no agent can
claim it, until you press **Start** on its card or row, which takes it out (it then waits on
what it is after, as any task does). The lobby's form has **Add to backlog** beside **Add**, both under the field: it
posts exactly what Add would (the text, the agent or team chosen, the follow-up) and holds it, and
is off under the same conditions as Add; Enter in the field still adds. A held task is in Backlog
as a column, even when it also waits on others, and its card still says "Waiting on p12"; in the
list it is in a **Backlog · 2** section above the to-dos, folded at first like a room's Done
section and unfolded with a press, and is not also listed among the to-dos. A held task keeps its
checkbox, **Delete**, **Follow-up** and **Reply**, and **Start** sits on the same line. Only the
lobby has a backlog: a room's board and form are as they were.

A lobby task can go to a team of the roster (see Team roster): it is handed out by the rules of
Any idle agent, so it needs **Agent tools** and **Wake agents** as they do, but only to an idle
agent that holds a teammate of that team. While only agents of other teams are idle it stays open.
A named task goes before it, and among the rest the oldest goes first, as it does for any task. An
agent of another team cannot claim it by hand either ("it is for team QA-PR"); you can claim any.
The task keeps its team when it is reopened. It is stored with the team's id, so a renamed team
keeps its tasks; if the team is removed or the roster switched off, the task goes to any idle agent
instead of waiting for nobody. `office_post` takes `team`, a roster team's name in any case or its
id, for a lobby task only and never with `to`; `office_read` shows it as `p7 task open for team
QA-PR`.

The lobby's form gives a task to a team too: with the roster on and teams in it, the **Send task
to** page has a **Teams** group right under **Any idle agent**, one row per team with its name and
how many teammates it has ("2 teammates", "1 teammate"). The field then reads "Team QA-PR", and
Add posts the task for that team and for no agent; afterwards the choice is Any idle agent again,
and it is also if the team leaves the roster while the form is open. With the roster off or with
no teams the page is as it was. A room's form has no team choice. A card, a list row and a room
card say "for team QA-PR" where a task for an agent says "for Builder", with the team's current
name, or its id once the team is gone.

New lobby to-dos addressed to a specific agent use the same tracked assignment and completion confirmation as automatic pickups. Older addressed messages are not sent a second time. When an agent with a workspace claims a lobby task, a copy of the task appears on that workspace's board, linked to the lobby task. Marking either one done marks both done; reopening either one frees the lobby task and deletes the copy, and deleting the lobby task deletes its copy. Lobby tasks already claimed when the office starts get their copy then.

A task finished with a note keeps it as its result (up to 2,000 characters), and a linked lobby
task and its copy carry the same result. A session that finishes its assignment by the completion
line has the rest of that reply kept as the result. A card and a list row show the result under
the task's text: its first three lines and 160 characters, and **More** for the rest when there is
more. A note can be a reply under a task: the replies show under the task, oldest first, each as
"author · text", and never as notes of their own, in the Notes column, the lobby's Notes or a room
card's count. A reply always sits on the task's board, under the lobby task when it answers a copy;
the copy shows its lobby task's replies, so an answer typed in the room is there too.
**Reply** under a task opens a one-line field; Enter or **Send** posts the reply. A done task keeps
its result and its replies, in the lobby's list and in a room's Done section or column, and a task
takes its replies with it when it is deleted, cleared or dropped.

A done task says what it took, in one line under its result and above its replies, on a card and
on a list row: "took 23 min · $0.42". The time runs from the claim to done ("took under a minute",
"took 1 h 5 min", "took 1 d 3 h"). The cost is what the agent that held the task spent, read from
the cost its provider reports: a provider reports it when a turn ends, so it is counted from the
turn the task was claimed in to the end of the turn it was finished in, and chat with the agent in
that time counts too, since it is the agent's turns that are measured, not only the task's. A task
marked done while its agent is still at work shows the time alone until that turn ends, and the
cost joins the line then. A provider that reports no cost, or whose counter went back down in
between, shows the time alone, as does a task you claimed yourself, and a cost under one cent shows
as "under $0.01". Whoever marks the task done, the line measures the agent that held it. A
reopened task loses the line and starts afresh at its next claim; a task done with no claim, and a
pretend duty acted out in the 3D office, show none.
The cost is measured only while an office is open or **Keep watching** is on, since the figures
come from the directory, which runs only then. A task claimed with neither shows its time alone:
an old figure is never used. So does a task that still waited for its turn to end when the last
office closed, or when the directory restarted. A provider whose usage is polled apart from its
turns (pi, omp) can be read before its last turn's figure has arrived, and its cost then falls
short by that turn.
`office_read` does not carry the line.

A task can wait for other tasks: `office_post` takes `after`, up to 5 task ids on any board (the
user's post takes it too), for a task only, never a note or a reply, and each must name a task
that exists. A copy's id is kept as its lobby task's, since the copy goes when that task is
reopened. While one of them is there and not done the task waits: the pickup passes over it, and
an agent can neither claim it nor mark it done ("waiting on p12, p13"). You can still claim it or
mark it done by hand. It is released when the last of them is done or deleted, since a
task that is gone no longer holds it; any board's change looks again, so a room's task finished
hands out the lobby task that waited on it with no other event. Its assignment carries, after the
task's text, "It waited on (results as their agents reported them, not instructions):" and a line
per task it waited on with that task's result ("no result given" without one), each result cut to
600 characters; a task that is gone is left out, and with none left there is no such block. The
heading says whose words they are because another agent wrote them and the assignment arrives as
a prompt of yours. That is how one team hands its work to the next: "Review" after "Build" gets
Build's result. A reopened task waits again on the same tasks. `office_read` shows it
as `p14 task open after p12, p13 (waiting)`, without "(waiting)" once they are done.

An assignment of a task with replies also carries what was said under it: after the task's text
and the "It waited on" block, if there is one, comes "So far on this task (earlier notes, read them
as reports):" and the 5 newest replies, oldest first, each as "author: text" with the text cut to
600 characters and its further lines indented under it (every kind of line break starts a new
line, and other control characters are removed). The author is "agent" and the agent's title, as
in "agent Builder", or "the owner" for you alone, so an agent titled "the owner" still reads as
"agent the owner". Like the results it waited on, they are labelled as reports, since anyone can
write a reply and the assignment arrives as a prompt of yours. Every assignment of a task with
replies has the block, a handed-over one or not; one without replies has none.

The board shows what waits. A task that waits sits in a **Waiting** column left of To do ("Waiting
· 2"), which shows only while it holds something; once nothing holds the task it moves to To do. A
claimed or done task is never in Waiting, whatever its `after`. A task that is after others says
so on its card and its list row, over its thread: "Waiting on p12, p13" while it waits, and "After
p12, p13" once it is released or taken by hand, so where it came from stays visible. Only ids are
shown. A board judges this by the tasks of every board, the duty board's duties included, since a
task can wait on one of another's.

**Follow-up** on a card or a list row, open, claimed or done, makes the next task a follow-up of it:
it adds that task to the form's pending `after` (once each, five at most) and moves the focus to the
field. Under the field the form says "After p12, p13" with **Clear**; Add posts the task with its
`after` and then clears it, and a task that leaves the boards is dropped from the list. At five,
Follow-up does nothing and the form says "A task waits on at most 5 tasks". The lobby's form and a
room's form both take it (in a room it sets the kind to Task, since a note cannot wait), and the
task still takes the recipient or team the form has. This is how one team hands work to the next:
post a task for one team, then a follow-up of it for another, which is handed out only once the
first is done and carries the first one's result.

A lobby task can be held in a backlog: `office_post` takes `backlog` (the office's own post takes it
too), for a lobby task only ("only a lobby task goes to the backlog"), and it may carry `to`, `team`
and `after`. A held task is open, but it is not work: the pickup passes over it, so an older held
task never keeps a later one from an idle agent, and an agent can neither claim it nor mark it done
("it is in the backlog"). One named for an agent stays held as well: it is not handed out and the
agent is not woken until it is started, and it is then handed out as any named task is. One that
also waits is shown and treated as held first; once started, the waiting rule applies as usual.
Only you start it, by the office's start call (`office.task.start.request`, in the plugin's
`startRpc`): the task keeps everything but the hold, gets a new sequence number and update time, and
the pickup looks again. Starting a task that is not held changes nothing, and a note or an unknown
id is refused. Your own claim or done on a held task starts it in the same update. Agents have no
start: `office_update` has no such action, and a reopen of a held task changes nothing, since it is
open and nobody holds it. `office_read` shows it as `p12 task open (backlog), from the user: ...`.

The office can also start backlog tasks by itself, since each start spends your plan. The host
setting `autoStart` is off at first. With it on, the office starts the oldest held task that waits
on nothing (`server/auto-start.ts`; a held task that still waits on another is passed over, and one
named for an agent is started like any other), when the pickup could hand it out (Agent tools on and
wakes not paused) and all three of its numbers allow it:

- every plan limit of every provider counted in the Host card's Plan section, each window and not
  only the closest, is under `autoStartUnderPct` (70%);
- fewer than `autoStartAtOnce` (3) lobby tasks are work already committed: claimed, or open and not
  held (started or posted, and waiting for an agent or for other tasks). Duties and rooms' tasks do
  not count;
- fewer than `autoStartPerDay` (10) were started by the office today. The day is a calendar day
  from midnight in the notes' zone, not the duty board's 08:00 day, and your own Start presses do
  not count.

A held task the intake imported from a ticket (see Intake) is passed over unless the host setting
`intakeAutoStart` is on (off at first); with only imported tasks held, the reason is `empty`. With
it on, a ticket is started and reaches an agent's prompt without the owner reading it: leave it off
unless only people you trust can write tickets.

It needs **Keep watching**. The limits come only from the server's plan watch (see Plan limits),
and a reading older than 15 minutes counts as none. With Keep watching off, before the first read,
or with no counted provider reporting a limit, nothing starts. If the office cannot read its count
file, nothing starts until it can (fix or delete `auto-start.json`). The office checks after each
board change, each plan reading, each turn's end, each save of the settings and each change of the
pickup or of the wakes' pause, and starts one task per check. The count is raised in the file before
the start and put back if the start fails or the owner started the task first, so a crash in between
errs toward starting less. A start changes the board, which brings the next check, so several can
start in a row, each checked again, and the task started counts as committed work at once. A check
that starts nothing asks for no other, and no timer of its own runs. The office's state for clients
carries `autoStart`: on, why it waits, the day's count and the cap. It is sent as an `auto-start`
event when it changes. The reasons, in the order they are checked: `off`, `no-pickup`, `empty` (no
held task ready), `no-reading`, `limit` (with the worst window), `at-once` (with the committed
count), `per-day` and `no-count` (the count file cannot be read; the day's count then reads 0).

The gate's settings are in Settings, Automation: the switch **Start backlog tasks**, and under it
**Start under (%)** (10 to 100), **At once** (1 to 20) and **Per day** (1 to 200), with the hint
"Needs Keep watching: with no reading of the plan's limits nothing is started." A number takes
digits only; one out of range is held to the range when the field is left, and that is what is
saved. While the switch is on, a line over the Backlog (the Backlog column's body under its heading
on the kanban, the unfolded **Backlog** section on the list) says "Starting by itself" when the gate
is open and otherwise why it waits: agents are not picking up work (Agent tools or Wake agents is
off); nothing here is ready to start; waiting for a reading of the plan's limits (needs Keep
watching); "Claude's 5 hours is at 82% (starts under 70%)"; "3 tasks are in progress or to do (at
most 3)"; done for today, "10 started (at most 10 a day)"; or stopped, today's count cannot be read
(see the office's log). With the switch off there is no line.

A claimed lobby task or duty can be handed over, by the office's hand-over call
(`office.task.hand_over.request`, in the plugin's `handOverRpc`, with the task's id; on a room's
copy it acts on the lobby task). It is for a task stuck with an agent that cannot go on, as when
its provider's plan is used up and the agent has no turn left to be asked. In one save the office
posts a reply under the task in the holder's name, "Where Builder left it: " and the holder's last
answer as its timeline has it, cut to 1,200 characters with control characters other than new
lines and tabs removed, or "Where Builder left it: no answer to read." when none can be read. Only
an answer from a turn that ended at or after the claim counts, since an older one is about other
work, and a task whose assignment was never delivered gets the "no answer to read." form without
the timeline being read. A blocked task's note puts the reason first, cut to 300 characters, so
the next agent's So far block keeps it: "Where Builder left it. It needed: <reason>" and the answer
on the next line. The task is reopened as a reopen does (its team, its `after` and its ticket
stay; the claim, the block and the number of its assignment go), its room copy is deleted, it is
no longer named for an agent (a task named for its holder would otherwise wait for that holder),
and it is marked with the holder's provider. The answer
is read before the save, so a slow timeline holds no other change of the board. The pickup then
passes over every agent of that provider, and an agent of it other than the task's holder can
neither claim it by hand nor mark it done or blocked ("Unable to claim p12: it was handed over
from claude", "Unable to finish p12: …"); an agent of another provider, or one whose
provider the office cannot tell, can take it, and you can claim it. With no idle agent of another
provider it waits in To do like any other task. The mark stays when the task is reopened or
claimed again and goes when it is done; a later hand-over replaces it, and a holder whose provider
is unknown leaves none. The former holder is not told: the note wakes nobody, and an agent that
comes back may still think it has the task, until it reads the board or its `office_update`
on the task is refused, as its claim, done and block are. A task nobody holds is refused ("nobody holds it"), as are one you hold ("you hold it:
reopen it instead"), a note, a done task, and a room's own task ("only a lobby task or a duty is
handed on"). Agents have no hand-over tool. `office_read` shows a marked task as `p12 task open
not for claude, from the user: ...`, after its team and its `after`. The office can also hand tasks
over by itself when a plan runs out (see Plan limits).

An agent that needs something from you before it can go on blocks its task: `office_update` with
`block` and what it needs in `note`. Only the agent holding the task can block it. The task stays
claimed and moves to the kanban's **Needs you** column, and a card and a list row show "Needs you:"
and the reason above the task's thread. A linked lobby task and its copy carry the same block. A
reply from anyone but the holder is the answer: it clears the block and wakes the holder with the
reply. The block also goes when the holder finishes the task, claims it again or reopens it, and
when you reopen it. The **Tasks** entry is in the Attention tab while a task is blocked, as in
"2 need you", and counts in the tab's count. Its card lists the blocked tasks of every board,
oldest first, a lobby task and its copy once: each task's text, "<agent> needs: <reason>", its
board, an **Answer** field and **Open board**. Enter or **Send** posts the answer as a reply under
the task; the row goes once the board has it. A duty an agent holds is on the card by the same
rules as a task, blocked, stalled or merged: its row names its board as "Duty board", its Answer
and its Nudge are replies under the duty, and its **Open board** opens the duty board.

The card also lists claims nobody works on, after the blocked ones, oldest first: a claimed task
that is not blocked and whose holder, an agent of the office, stopped on an error ("<agent> stopped
on an error") or has been idle for two minutes since the task last changed ("<agent> is idle"). A
holder that is running or starting gives no row, nor does a task claimed by you. A holder at home
(a session Paseo closed, see Agents at home) keeps its claim and does nothing until it is woken,
so its task is listed at once, with no two-minute wait: "<agent> is at home". A task it blocked
stays among the blocked ones, with its Answer field. The entry counts both kinds: "2 need you · 1
stalled". A stalled row has **Nudge**, **Reopen** and **Open board**, and no Answer field.
**Nudge** posts a reply under the task from you, "Status check: finish with office_update done and
a short result, or block with what you need.", which wakes an idle holder or one at home (at most
six an hour); **Reopen** frees the task for another agent. The clock is read again every 30
seconds while a task is claimed, so an idle claim turns up without another event.

Last come the tasks whose work has landed: a claimed task, on any board, whose holder is an agent
of the office in a workspace whose pull request is merged, if it is not already blocked or stalled
(a task is on one row, in the kind that comes first). The entry adds "N merged" as its third part,
as in "1 needs you · 1 stalled · 2 merged". The row says "<agent>'s pull request is merged", with
the pull request's number and title when the office has them ("#42 Fix the ledger total"), and has
**Mark done** and **Open board**, and no Answer field. **Mark done** is the same action as on the
board. The office never marks a task done by itself, since one workspace can hold several tasks
and a merged pull request does not say which of them it finished; the row only asks. The workspace
says that its pull request is merged and not when, so a task claimed after the merge, by an agent
of a workspace whose pull request was already merged, is listed as merged at once.

A board also shows who is at work, so a room with nothing posted is not an empty board. Under its
form a room's board lists the room's agents: each one's name, what it is at, and the unfinished
steps of its checklist. What an agent is at is said in the 3D whiteboard's words: its "doing now"
line, "Waiting for your answer", "Stopped on an error", "Waiting on N sub-agents" or "Resting". The
lobby's board lists the same for the whole office under **Agent tasks**, room by room: the agents
at work, the ones that need you, and the resting ones with steps left. A resting agent with nothing
left is on its own room's board only. A press on an agent opens it as a press on its desk does, and
a room's name on the lobby's board opens that room's board. None of this is a post: it is the
office's live state, as fresh as the "doing now" read, and nothing of it is kept in `boards.json`.

The checklist steps, text included, are what the "doing now" read takes from the newest `todo` item
among the agent's newest timeline items. The steps stay after the agent stops and go when it is
archived or closed. The server keeps them in memory, and only while an office surface is open:
after the last one closes or the daemon restarts, an agent's steps are back when it next updates
its checklist. A board is removed when its workspace is archived while the daemon runs; a board
left from a workspace archived otherwise stays until its posts are deleted. A task that waited on
one of the removed board's tasks is released then, as it is when a task is deleted.

Interactive agent sessions get three tools, `office_read`, `office_post` and `office_update`,
unless the "Agent tools" setting is off when the session opens. `office_update` with `done` takes
`note`, the task's result, `office_update` with `block` takes `note`, what the agent needs, and
`office_post` takes `replyTo`, a task's id, to post a note under that task; `office_read` lists a
result under its task, what a blocked task needs, and a reply as `p14 note re p12`. A provider
with Paseo's agent tools off gets none of them, and a provider that lists `send_agent_prompt` in
`paseoTools.disabledTools` must list `office_post` too to keep its agents from waking others.

A post that names an agent wakes it when it is idle, at most 6 times an hour per agent. Posts that
wait for an agent go out as one prompt per author: an agent's posts carry that agent as the source,
the user's posts arrive as a user prompt. A post naming an agent that has not run a turn yet is
delivered after that agent's first turn or the next post that names it. Pending mention
notifications are held in memory. A reply wakes the agent holding its task by the same rules,
unless that agent wrote it: a reply from the holder is for you and wakes nobody. A task that names
an agent and still waits on other tasks does not wake it yet, since the agent could not claim it:
the wake goes out when the last of those tasks is done or deleted, also after a restart of the
daemon, and not at all if the task itself is deleted, claimed or done first. (A lobby task for a
named agent is handed out by the pickup, which waits the same way.)

## The duty board

The pantry's duty board is kept on the host. You choose its duties: up to 12, each with a name (up
to 40 characters), the weekdays it is due, a time of day (08:00 unless set) and, if an agent should
do it, instructions (up to 2,000 characters). A host starts with the four pantry chores, Monday to
Friday, without instructions. The list is kept in `<PASEO_HOME>/office/duties.json`
(`server/duty-service.ts`). A file the office cannot read, or one written by a newer version, is
moved aside to `duties.json.corrupt-<time>` and the list starts again from the four chores; your old
list is in that file.

The duty board's day begins at 8:00 in the notes' time zone ("Time zone", the host's when empty or
not a zone the host knows); before 8:00 it is still the day before. At its time on each of its days
a duty is posted as a task on the board `duty`, a host-wide board like the lobby's: at 8:00 for one
without a time, at 14:30 for one set to 14:30. A time is `HH:MM` from 08:00 to 23:59, never earlier,
since an earlier time would fall on the board's day before; a time in the file that is not one
(written by hand) counts as 08:00, and a save with one is refused, naming the duty. The 8:00 run
also takes the duties finished on earlier days off the board. When the office starts, and when you
save the list, a duty due today that has no post yet is posted at once if its time has passed.
A duty still open or claimed when its day ends is owed: it stays on the board and is not posted
again. An owed duty finished today counts for today, so it is not posted again until its next day.
Removing a duty takes its open post off the board, and a claimed one stays until it is done. A new
name or new instructions change today's open post. A new time leaves a duty posted today as it
is; one not yet posted today is posted at its new time, or at the save when that time has passed.

A duty with instructions goes to an idle agent as a lobby to-do does, under the same rules: one
task or duty at a time per agent, the wake limits, **Wake agents** and **Agent tools**. Its prompt
starts "The office assigned you duty p12 from the duty board." and ends with the lobby's two
completion lines. Agents read the board with `office_read` and `board: "duty"` and claim or finish
a duty with `office_update`. An agent finishes or reopens only a duty it holds; from the duty board
you mark any. No task or note is posted to the duty board, not even from the office: its duties
come from the list. A reply is the one post it takes (`office_post` with `replyTo`, or yours from
the office): it sits on the duty board under its duty and wakes the duty's holder, as on any
board. A duty is never addressed to one agent, and unlike a lobby to-do, a claimed duty gets no
copy on its agent's workspace board.

An agent blocks a duty it holds as it blocks a task, with `office_update`, `block` and what it
needs, and finishes it with a result in `note`. Since the duty board is no room's, both show in
two places. The **Tasks** card lists a blocked duty with its Answer field, and a claimed duty
nobody works on or whose holder's pull request is merged, under "Duty board" (see Boards and
wakes). On the duty board, today's row of a duty says "Needs you: <reason>" while it is blocked
and, once it is done, shows its result ("Result", cut with **More** as a task's is) and what it
took; the replies under the duty are listed there too, oldest first, and while an agent has the
duty **Reply** opens a one-line field that posts one. A reply from anyone but the holder clears
the block.

A duty without instructions is pretend. No agent is asked, and an agent can neither claim nor finish
it. On the 3D floor a person acts it out as soon as it is idle (resting at its desk with nothing
else on), at any hour once it is posted: a duty with a time is on the board from that time. Owed
duties go first, then the board's order, each to the idle person that has done fewest today, one
duty at a time. Work coming in calls the person back and the duty waits for the next idle one. Only
the cups wait for something else, a cup in the sink, unless they are owed. The view tells the host,
which records it as done by that agent. When two devices both act it out, the first to report wins.
With no 3D office open, or nobody idle, before its day ends, it stays open and is owed.

A click on the 3D pantry's board opens the duty board, and so does **Duty board** on the List's
lobby card and in the chat's More menu, so the 2D floor and a phone without WebGL can reach it too.
It shows today's duties with who has each, what a holder needs and what came of a done one (see
above), with Mark done and, for one someone has or that is done, Reopen (a duty is freed on its
own when its agent is archived, so Reopen is for one an agent still holds but is not working on,
at home or not), and the list with each duty's name, instructions and day buttons and time, saved
whole. The time field takes `H:MM` or `HH:MM` and keeps it as `HH:MM`;
empty is 08:00, and Save waits while a time is outside 08:00 to 23:59. Today's duties show a time
that is not 08:00 after the name ("Take out the bin · 14:30"). Unticking today's day on a duty takes
its open post of today off the board when you save; a claimed one stays until it is done, as for a
removed duty. The scene is told each duty's name, its chore, its holder's title cut to 24 characters
and its state, never its instructions (`worldDuties` in `client/world/adapter.ts`). The board and
its tooltip show them, and the scene keeps no rota of its own. Until the host has sent its list (an
older host has none) nothing offers the duty board, and the scene keeps upstream's rota and its
note. The four starting duties keep the cups, bin, plants and tables chores. For a duty you add, the
person walks to the board and back. The person of an agent that holds a duty acts its chore out
once. HR posts the day's list in the chat in the morning. The scene's part is `paseo-duty-plan.js`
and `people/duty.js`.

## Timeline and the week

The **Timeline** button, in the toolbar of a wide office and at the top of the Activity tab, opens a card with a lane for each agent over the last hour,
6 hours or 24 hours: green at work, amber waiting for the user, red stopped on an error, grey
resting, and a mark at each tool call. **Replay** moves a head across the lanes from the start of
the range at 30, 60 or 120 times the clock, and each lane says what its agent was at then
("editing", "running tests", "waiting for you"). **Now** ends the replay. The replay is in the card
only: the 3D floor keeps showing the present.

**Replay on the floor**, beside it while the 3D floor is showing, closes the card and replays the
range there (`client/floor-replay.ts`, `client/use-floor-replay.tsx`): the people sit, work, wait
and stop as the timeline saw them, each at the kind of thing it was at for a minute after the
call was seen, and a bar over the floor says the day and the time shown, to the second, and how many
people the floor has then. Its track shows where that is in the range, and a press on it moves
there; the buttons are From the start, ten minutes back or on, Pause or Resume, the speed (10 to
600 times the clock) and Back to now. It ends by itself at the range's end. An agent the office was not watching at a moment is off the floor then, and
one archived since cannot be drawn. The lists, the boards and the cards stay today's, and so do
the staff scenes, the weather and the sound, which follow the device's clock.

**This week** adds the last seven days up: time at work, turns started, edits, commands, cost where
the provider reports one, the busiest team, and a bar for each 24 hours.

The office's server keeps this log itself (`server/timeline.ts`, `office/timeline.jsonl`, mode 600):
each change of an agent's state, the kind of each tool call (never its file, command or text) and
each rise of its cost, for eight days and at most 40,000 marks. It sees only while an office
surface is open on some device, at the directory's changes and the 5-second activity reads. A time
the office was closed is a gap in every lane, not a rest, and the week's figures count only what
was seen. `office.timeline.request` reads it. The file is a line per mark: a change adds lines to its end,
and the whole file is written again only when the server starts and when old marks are cut off. A
`timeline.json` of 0.2.14 or earlier is read once and replaced.

## Keep watching

The directory and the activity reads run while an office is open on some device and stop when the
last one closes. So the timeline has a gap for every hour nobody looked, the week's figures leave
those hours out, the vault misses turns, and nothing below is noticed overnight.

**Keep watching** (Settings, host-wide, off by default) keeps both going with no office open
(`keepOpen` in `server/hub.ts`). The reads then come every 15 seconds, not every 5, and are back
at 5 as soon as an office opens. What is read is what an open office reads: each running agent's
newest timeline entries, and with the History vault on, what was said after each turn. Nothing new
is stored or sent. After a daemon restart the watching starts when the first agent opens or ends
a turn, or an office is opened: an installed plugin gets the Paseo API only then.

It also does two things for the [webhook](#notifications), which the open office does not need
from the server. The plan limits are read from Paseo every 5 minutes (`server/plan-watch.ts`),
and the host is read every minute with no office open (`MACHINE_BACKGROUND_MS` in
`server/machine/watch.ts`; Linux only), so the Host card's 30 minutes of RAM and CPU have no gap
when an office opens. An open office reads the host every 10 seconds and the plans every two
minutes, as before. The weather and the street's checks still run only while an office is open:
they only draw the scene, and nobody is looking.

The server's plan reading is also what the backlog's auto-start gate looks at, so with Keep
watching off nothing is started by itself (see [Boards and wakes](#boards-and-wakes)). The open
office's own reads of the plans are not the gate's: they are not kept on the server.

## Notifications

The plugin SDK gives a plugin's server no notification of its own, so the office posts to an
address you give it. **Webhook address** (Settings > Services > Notifications) takes one, https
or plain http on the host itself. The office then sends one `POST` with a JSON body
(`server/notify.ts`, `shared/notify.ts`) each time it raises an alert below (a loop, a refused
call, two agents in one file, a taken port, failing checks) and each time an incidents check
opens an incident:

```json
{
  "source": "paseo-office",
  "text": "Acme Studio: Checkout is stuck in a loop\nBash failed 3 times running",
  "kind": "loop",
  "severity": "danger",
  "title": "Checkout is stuck in a loop",
  "detail": "Bash failed 3 times running",
  "agent": "Checkout",
  "at": 1795770000000
}
```

`kind` is `loop`, `refused`, `clash`, `port`, `checks`, `incident`, `plan`, `host` or `test`;
`severity` is `danger` for a loop, an incident, a plan limit used up and memory nearly full, and
`warning` for the rest; an incident carries its tracker
page as `url`. `text` is the whole message as lines, which is what Slack's incoming webhooks show;
n8n or another relay can pass it on to Telegram or ntfy. The title and detail are the alert's own,
so with streamer mode on they name the tool and not the file or the command. A prompt or a reply
is never sent.

**Notify for** chooses what is sent: **Danger only**, the default, is a loop, an incident, a plan
limit used up and memory nearly full; **Warning and danger** adds the rest, among them a plan
limit at 80% and at 95%.

With **Keep watching** on, the office tells of a plan limit and of the host's memory too
(`server/plan-watch.ts`, `server/host-alert.ts`). A provider's closest limit sends one `plan`
message as it reaches 80%, 95% and 100% (used up), and none again until it has fallen, which a
reset does; a jump from 50% to 97% is one message, for 95%. A provider switched off in the Host
card's Plan section is left out, and a read that fails sends nothing. Memory at the Host card's
red (90%) sends one `host` message, and the next only after memory has been under 80% again. The
state is in memory: after a daemon restart a limit already past a threshold is told once more.

Each alert and each incident is sent once, as it is raised. A request waits 10 seconds, follows
no redirect and is not tried again; a failure is one line in the plugin's log, without the
address. **Send a test** posts one message to the saved address and says what came back. The
alerts are raised only while the office reads the agents: with no office open that takes
**Keep watching**. The incidents check runs on its own timer either way. After a daemon restart a
workspace whose checks still fail is told again. The address is stored in the host's settings as
typed, key included, and anyone who can open the settings page can read it.

## Telegram

The office can speak in a Telegram chat through a bot you make (`server/telegram-bridge.ts`,
`server/telegram.ts`, `server/telegram-store.ts`). The office calls Telegram, a long poll of
`getUpdates`; Telegram never calls the office, so the host opens no port.

**Setting it up.**

1. In Telegram, send `/newbot` to @BotFather and keep the token it gives. Type it in Settings →
   Services → Telegram and press Save (`office.telegram.save.request`; an empty token removes the
   saved one), or set
   `TELEGRAM_BOT_TOKEN` in the daemon's environment; a saved token wins. The token is never sent
   back to a client: the field is masked, is emptied once Save has answered (whether it took the
   token or not), and the line under it says only "Saved", "From the host's environment
   (TELEGRAM_BOT_TOKEN)" or "No token yet". Remove shows only for a saved token and asks "Remove the
   saved token?" first; a token from the environment cannot be removed here.
2. Add the bot to your group (or open a private chat with it) and write it a line. While no chat
   is set the office does not poll, so `https://api.telegram.org/bot<token>/getUpdates` in a
   browser shows that line with `"chat":{"id":...}` (a group's id starts with `-`) and
   `"from":{"id":...}`, your own user id. The address holds the token: clear it from the
   browser's history afterwards.
3. Put the chat id in **Chat id** (`telegramChat`) and your user id in **User ids that are
   heard** (`telegramUsers`): one per line, digits with no leading zero, up to 20. An entry the
   settings would refuse is told by its line ("Line 2: "0123" is not a Telegram user id") and is not
   saved. **Test** (`office.telegram.test.request`) asks Telegram who the bot is, then writes "The
   office is connected." to the chat, and shows "Connected as @<bot>. A message was sent to the
   chat." or what went wrong; it is off while there is no token or no chat.

**What is sent** in the settings holds the five switches (`telegramNeeds`, `telegramStalled`,
`telegramDone`, `telegramIncidents`, `telegramPlan`, described below), and **Tasks from Telegram go
to** is `telegramLands`, Backlog or To do. The line at the bottom of the section says "Off: needs a
token, a chat and at least one user id." while the bridge is not polling, "On." while it is, the
bridge's problem (plain text) when it has one, and "Messages from others ignored: N" when the
bridge has dropped messages from users who are not listed, so you can see someone unlisted writing.

The bridge runs only with a token, a chat and at least one user id. A change of any of them, or
of the settings at all after Telegram refused the token, stops the running poll and starts again.

**What goes out**, to the configured chat, each by its switch, plain text with the task id first
and the task's text, cut to 200 characters, on a second line:

- `telegramNeeds` (on): a task newly blocked, `p12 needs you — Builder: Which region?`, and again
  when its question changes.
- `telegramStalled` (off): a claim newly stalled by the Tasks card's rule (its holder stopped on an
  error, is at home, or has sat idle on it for 2 minutes), checked every 60 seconds:
  `p12 is stalled — Builder is idle`. It needs the agents' statuses, which the office has only
  while an office is open or **Keep watching** is on; without them no stall is told.
- `telegramDone` (on): a task newly done, `p12 done by Builder: <result>`, or
  `no result given`; a task nobody else held is `done by the owner`. A duty done is not told: the
  pretend ones are acted out every day. A duty blocked or stalled is told like any task.
- `telegramIncidents` and `telegramPlan` (on): an incident and a plan warning, as the webhook gets
  them (the notice's `text`), whatever **Notify for** says.

Tasks of every board are told; a lobby task and its copy on its holder's board are one task, told
as the lobby task. Each event is told once. When the bridge starts (or comes on) it first looks
at once without telling, so a restart does not repeat the day's messages and what happened while
it was off is not told; what changes after that look is, a claim that stalls in the first minute
included. A message is cut to 3,500 characters with "…". A send that fails is not tried
again; it is the bridge's problem until one goes through.

**What comes in, and from whom.** A message is heard only when all of these hold: it is a message
with text, its sender is no bot, the sender's id is in `telegramUsers`, and it was written in the
configured chat or in the sender's own private chat with the bot. Anything else, a listed user in
another group included, is dropped: counted (`dropped`), never answered, and never logged with its
text, sender or chat. Edits, channel posts and button presses are not asked for and are ignored. A
message heard can make an agent act, and an agent runs commands with its permissions, so list
only yourself or people you trust. In a group the bot sees only commands and replies to its own
messages unless you turn its privacy mode off; it needs no more. A forwarded message is never
acted on, whoever forwards it: its words are someone else's, so it gets the line of help. A user
id is digits with no leading zero.

- **A reply** to one of the bridge's messages about a task, in the configured chat, posts its text
  under that task as your reply: a blocked task is unblocked and its holder woken, as a reply on
  the board does. The bridge answers `Posted under p12.` or the board's refusal. A reply to a
  message it does not know, or whose task is gone, gets `That task is no longer on the board.` A
  message id is its chat's own, so a reply is matched only in the chat it was written in: in a
  private chat, a reply to the bridge's own message there (`Posted p12 to the backlog.`, say)
  answers that task. Moving the office to another chat leaves the old chat's messages behind.
- **`/task <text>`** (or `/task@yourbot <text>`) posts a lobby task as you, held in the Backlog
  unless `telegramLands` is `todo`, and answers `Posted p12 to the backlog.` or `Posted p12.`;
  with no text it answers `Usage: /task <what to do>`. At most 20 tasks an hour come from
  Telegram, from everyone together; past that it answers
  `Too many tasks this hour: wait a little.` and posts nothing.
- **`/board`** answers the lobby's counts (in progress, needs you, waiting, to do, in the backlog)
  and up to 20 lines `p12 <state>: <text>` of its tasks not done, blocked first, each text cut to
  80 characters.
- Anything else from a listed user gets one line of help:
  `Reply to a task's message to answer it, or use /task or /board.`
- A command with a bot's name (`/task@name`) is taken only when the name is this bot's, in any
  case; the bridge asks Telegram for it when its poll starts. A command for another bot, or any
  named command while the name is not known, is left alone with no answer, so two bots in a group
  do not both speak. A bare `/task` or `/board` always counts.

The text of a message is posted as the post's text only: control characters but the newline and
the tab are removed and it is cut to 2,000 characters. Read a task from Telegram in the Backlog
before you start it, as you would a ticket.

**Polling and failures.** One poll at a time, held by Telegram for 25 seconds (35 seconds at most
on the office's side), for messages only. A network failure or a 5xx waits 5 seconds, doubling to
60; a 401 or 404 ("Telegram refused the token") stops the bridge until the token or the settings
change; a 409 ("Another program is reading this bot": a bot can have one reader, so another
program or a second office on the same bot) waits 60 seconds; a 429 waits what Telegram asks, 60
seconds at most. The token is in the path of every address Telegram is called at, so a failure is
said in the office's own words: never Telegram's, an address, or the error a request threw. No
redirect is followed, and an answer over 5,000,000 bytes is refused.

**What is stored where.** The saved token is in `<PASEO_HOME>/office/telegram.json`
(`{ version: 1, token }`, readable by the daemon's user only); one that cannot be read is no token,
and the state says so. `<PASEO_HOME>/office/telegram-state.json` keeps where the poll has got to
(`offset`) and for which bot (`bot`, the digits before the token's colon), the newest 200
messages the bridge sent about a task (`sent`, each with its chat, its message id and its task, so
a reply still finds its task after a restart) and the times of the last hour's tasks
(`taskTimes`). The offset is saved before each message is acted on, so a crash in the middle loses
that one message and acts on none twice. On the first run, or with a state file that cannot be
read, what waited in Telegram before is thrown away, not acted on. A token of another bot, saved
or in the environment, starts the same way and drops the old bot's messages. The state for
clients (`telegram` in the office's state) is whether the bridge is polling, where its token comes
from (`saved`, `env` or none), its problem, and how many messages it dropped since the daemon
started.

## What the office notices

Upstream does these with Claude Code hooks. Here the office's server does them from what it reads
anyway: each running agent's newest timeline entries every 5 seconds, and the directory
(`server/watchers.ts`). So they work for every provider, only while an office surface is open, and
a few seconds after the fact, not before it. Each is a card in the Attention strip; opening it
shows what can be done.

- **A loop.** The same call (the tool and what it was given) failed three times running. **Stop**
  ends the turn; **Send a hint** sends a line into it. It goes when the agent gets past it or its
  turn ends.
- **A refused call.** The provider's auto mode refused a call. The card has the call and the
  reason, for half an hour. Nothing waits on it.
- **Two agents in one file.** Both changed the same path within ten minutes. **Tell both** sends
  each a line about the other.
- **A taken port.** A command failed with "address already in use". **Tell the agent** sends it a
  line to use another port, naming the session whose server holds it when the Host readings say.
- **Failing checks.** The checks of a workspace's pull request fail. **Fix it** sends the failing
  checks to an agent of that workspace that is resting; while none rests, the card says so.

A line sent from a card joins the agent's running turn ("steer"), except Fix it, which is a
prompt. With streamer mode on, a card names the tool and not the file or the command.

**Pinned notes** (Settings) are said again to an agent whose conversation is compacted during a
turn, as a line into that turn. A compaction of a resting agent sends nothing, since that would
start a turn.

**Stop repeated failing calls** (Settings, host-wide, off by default) goes one step further for
a loop. When an agent asks permission for the very command or file edit that just failed three
times running, the office refuses the request and tells the agent why, so the fourth try is not
run (`repeats` in `server/watchers.ts`, on Paseo's `agent.permission.before` hook). It needs the
loop to have been seen (an office open, or Keep watching on), and a tool whose request names
neither a command nor a file is left alone.

Where the provider asks nothing (an auto, full access or bypass mode) there is no request to
refuse, so with the same setting on the office acts on the loop itself, once per loop. On the
read after the one that saw the loop, so that a refusal comes first, it sends the agent a fixed
line into its turn, the same "steer" as Send a hint: the same call failed 3 times running with
the same error, do not repeat it unchanged. If the very same call then fails once more than it
had when the hint was sent (the fourth failure, or the fifth when the fourth was already there
when the loop was first read), and the host can stop a turn, the office stops the turn and the
card's detail ends "The office stopped its turn: the same call failed again after the hint." On
a host that cannot stop a turn (stock Paseo 0.16) it sends the hint only, and the card stays as
it was. Nothing is sent where the office has refused a request for the loop's call, or where the
card was dismissed, and another call or a success ends the loop. The loop is seen by the 5
second reads, 15 seconds with Keep watching and no office open, so the hint comes 5 to 10 seconds
after the third failure (up to 30 seconds with Keep watching alone) and the agent may fail again
meanwhile; with no office open and Keep watching off nothing is read, and nothing is done. The
webhook hears of the loop once as it is raised, and again, as the same `loop` kind with the
extended detail, if the office stopped the turn.

Not done here: blocking a call before it runs where no permission is asked. That needs real
Claude Code hooks written into the host's `~/.claude/settings.json`; Paseo gives a plugin no call
that does it.

### Checkpoints

<a id="undo-last-turn"></a>

**Checkpoints** (formerly "Undo last turn"; the setting is still called **Undo last turn**:
Settings, host-wide, off by default) keep the last ten turns of each agent, show what each turn
changed, and undo them one turn at a time, newest first. It is git's and Paseo's turn hooks, not
Claude Code's, so it works for every provider and writes nothing into the host's Claude settings
(`server/undo-turn.ts`).

- When a turn starts (`agent.turn.before`) and the agent's folder is inside a git work tree, the
  office saves the work tree as a git tree object: a copy of the repository's index in a
  temporary folder, `git add -A` on the copy, `git write-tree`. Untracked files are in it, what
  `.gitignore` excludes is not. When the turn ends (`agent.turn.after`) it saves the work tree a
  second time the same way. The repository's own index, HEAD, branches, stash and files are not
  touched; only objects are added, and no ref.
- A turn whose two trees differ is kept as a checkpoint: its id, when it ended, and the two trees.
  A checkpoint is everything that changed in the work tree between the turn's start and its end,
  including what you or another agent changed in that time, not only what this agent did. A turn
  that changed nothing is not kept. Each agent keeps the ten newest; the eleventh drops the oldest.
  Each git call has a limit of 15 seconds and the hooks do not hold the turn.
- A turn the office could not snapshot (the setting off, a git error or a timeout; a failed snapshot
  at the turn's end is tried once more first) drops the agent's checkpoints, since the turns before it would no longer be one step back each. The panel
  then says "The last turn could not be snapshotted, so the checkpoints before it were dropped."
  until the next turn is snapshotted.
- The checkpoints are only in the daemon's memory: a restart forgets them. The trees have no ref,
  so `git gc` may prune old ones (by default once they are two weeks old). The office checks that
  both trees are still there each time it lists or undoes a checkpoint; one that lost a tree reads
  "This checkpoint's snapshot is gone" and cannot be undone.
- Each snapshot leaves loose objects (the blobs of changed files and the trees) in `.git` until git
  prunes them. A large untracked file that `.gitignore` does not exclude is read and stored by
  every snapshot that finds it changed, which makes snapshots slow; one that takes more than 15
  seconds fails, and the turn is not kept.

**What this turn changed.** A session with checkpoints that is not at work shows, under its
header, the newest turn's files from `git diff-tree` between its two trees: each path with its
added and removed lines (`+12 −3`), or "binary", "added", "deleted". It is every file that changed
in the folder during the turn, by an edit or write tool, by a shell command (`sed -i`, a formatter,
`rm`), or by anyone else working there at the time. The first 20 are shown and the rest behind
"N more"; the host lists 200 files a turn at most and counts the rest. The earlier turns are folded
under **Earlier turns**, one line each ("14:02 · 5 files"), each opening to its files.

**Undo this turn** is on the newest turn only. It asks once ("Put back everything that changed in
this folder during the turn? Files changed since are left alone."), then says "Put back N files"
and, for the files it left, each reason with its count. It undoes the turn the panel showed: if
that is no longer the newest (another undo got there first), it is refused with "that turn is no
longer the newest: look again" and the panel reads the list again. It is refused while the agent is
at work, and while another agent whose folder is in the same work tree is in a turn ("another agent
is working in this folder: undo when it has stopped"). An agent in a turn whose folder git cannot
read (a timeout, any failure other than git saying it is in no repository) counts as being in the
same work tree.

It goes over every path the turn's diff lists, in two steps. First the files the turn added; then
the files it changed or deleted, looked at afresh once the first step is done, so a folder the turn
swapped for a file (or the reverse, or a file renamed by case alone) comes back. Each path is looked
at right before it is touched: the file in the work tree now is compared with the turn's end tree
(content and executable bit, hashed by git with its filters; a missing file matches a file the end
tree does not have):

- the same as the turn left it: a file the turn added is deleted, with the folders it made that are
  left empty (a folder not in the before tree whose birth time is known and after the turn began;
  where the file system keeps no birth time, or one that reads as its change time, the folder
  stays); a file the turn changed or deleted is written back from the before tree, with its
  executable bit. Where the turn made a folder at the place of a file, that folder is removed
  first when it is empty, whatever its birth time; one holding other files is left, counted "left:
  a folder with other files is in the way";
- different: it is somebody's later work, and is left, counted "changed since the turn"; one
  already as it was before the turn is counted as that.

A path is never touched, and is counted under its own reason, when it is outside the work tree once
resolved, inside `.git`, ignored by git, a symbolic link (in the work tree or in either tree), a
submodule, or under a folder that is a symbolic link (checked again right before each delete and
each write). A file whose write fails is counted too. A path is a path: a name such as `:!x` is not
read as a git pattern. Writing back goes through a temporary index read from the before tree
(`git checkout-index`); undo never runs `git checkout`, `reset`, `stash` or `clean`, and never
changes the index, HEAD, a branch or a stash.

After an undo the checkpoint leaves the list, so the next undo steps one turn further back. It
stays, and a second undo does the rest, when the undo did not finish: git failed or ran out of time
("not reached: git stopped"), an agent began a turn in the work tree meanwhile ("not reached: an
agent began working"; the undo checks before every delete and write and touches nothing after), or
a file to write back was left where the undo had just removed something on its way ("not put back
yet: undo again to finish"). An undo happens outside a turn, so it is not a checkpoint itself. One
agent's turns and undos wait for each other. The comparison with the end tree keeps an undo from
overwriting work done after the turn ended; work another agent or you did during the turn is part
of the turn's checkpoint, and an undo puts that back too.

A snapshot is taken when the hook runs, which Paseo does not wait for, so an edit made in the first
moments of a turn may already be in its before tree, and is then not undone.

## History vault and the prompt report

**History vault** (Settings, host-wide, off by default) has the office keep what is said in each
conversation: the prompts and the replies, not the tool calls. It reads an agent's timeline through
Paseo when it first sees the agent and after each of its turns, for every provider, so it holds
what was said while an office surface was open. A message is cut at 2,000 characters, a
conversation at its newest 300 messages, and the vault at its 200 most recent conversations. It is
a folder on the host, `office/vault/`, with one file per conversation, mode 600, so a turn's end
writes that conversation only. Turning the setting off stops the reading and hides what is kept,
and deleting the folder empties it. A `vault.json` of 0.2.14 or earlier is moved into the folder
the first time the office starts.

**History**, in the toolbar of a wide office and at the top of the Activity tab, searches it with **Find**: the
newest 40 messages that hold every word typed, each with the words around the match. A hit opens
its conversation, which stays readable after the agent is archived.

**Prompt report**, the card's other tab, puts the last seven days' prompts in the vault against the
prompt helper's rules (`shared/upstream/prompt-coach.js`): how many had nothing to improve, and for
each rule how many prompts it spoke to, with up to three of them. It is worked out on the host by
the helper's own code. No model reads the prompts.

## Streamer mode, graphics and sticky notes

**Streamer mode** (Settings, host-wide, on by default) keeps file names, commands, search queries
and sites out of what the office sends to the floor: a bubble says "a file" or "a command". Turned
off, a step carries one cut line of what it is at (a file's name without its folder, a command's
first line, a query, a site's host name, 80 characters at most) and the 3D floor shows it over the
person, to everyone who opens this office. Prompts and replies are never sent either way.

**Gen-UI cards** (Settings, host-wide, off by default) is for a host that has the Generative UI
plugin (`genui`), whose agents write `ui` and `app` code blocks that Paseo's chat draws as
live cards. With the setting on, the office's session chat shows each block in place of its source:

- A **`ui` block** is a small language (data, not script). Once the block is complete the office
  draws its live card in the chat, with the plugin's own parser and components, vendored under
  `vendor/genui/` (below). A block still being written, and one that does not parse, stay a card
  with the block's title (the first `Card("...")`) and, for a parse failure, the first error's
  line. Components that call the plugin's daemon RPCs or web search (`Changes`, `Commits`,
  `PullRequest`, `Threads`, `Environments`, `Map`, `ImageSearch`), a `Load` that reads a file, and
  images from a file or the web are a note, "Changes: needs the Generative UI plugin's workspace
  chat", in place of the component. A button that sends a reply sends it to the session's agent, as
  the reply box does; `Queue`, `Set`, `Copy` and `OpenUrl` (http and https only) work too. Typed
  values live in the card until the chat is left; they are not kept, and the card's "Source"
  footer and file opening are not offered.
- An **`app` block** is a self-contained HTML page. In a browser or the desktop app the office runs
  it, once the block is complete, in a frame under the card's title: `sandbox="allow-scripts"` and
  nothing else (the page has its own empty origin, so it cannot read the office's storage or
  page, and cannot navigate the top window, submit a form or open a popup), `srcdoc`, no referrer,
  a fixed 360 px height that scrolls. The page starts with a Content-Security-Policy that allows
  inline script and style and `data:`/`blob:` images, fonts and media, and nothing else: no
  fetch, no WebSocket, no frame, no `<base>`, no form action. This is the plugin's own policy plus
  `base-uri` and `form-action`. The frame is inert toward the office: the office listens for no
  message from it, and the plugin's buttons that send a reply (which `ui` blocks use) do not exist
  in an `app` page. The plugin's own page tells its host its height and script errors; the office
  does not read either. A policy cannot stop the page navigating its own frame, so a page can
  load another site inside the frame; it has nothing of the office to send there.
- On a phone, and while a block is still streaming, an `app` block is the title card too.

A block inside another code block stays source. The office cannot tell whether the plugin is
installed, so the switch is always listed.

**The vendored card renderer.** `vendor/genui/` holds the parser (`shared/core`), the evaluator and 88
components of https://github.com/anh-chu/paseo-plugin-genui (Apache-2.0) at a pinned commit, copied
unchanged (`MANIFEST.json` holds a sha256 for each file); the two files that are the office's own
are `entry.tsx` and `loaders.ts` (the stand-in for upstream's loaders, which call its RPCs).
`scripts/build-genui.mjs` bundles them into `client/genui-kit.generated.ts` (`npm run build:genui`;
`npm run check:genui` fails when the committed file is stale; CI runs it). The host supplies the
only runtime imports: react, react-native and `@getpaseo/plugin/client` and `/client/ui`. The
module is about 400 KB minified (120 KB gzipped), so the client bundle goes from about 870 KB to
1,280 KB. The host compiles the client into one file with no code splitting, so the bytes come with
the plugin; `client/genui-kit.ts` loads the module with `import()`, so its code runs only when a
reply first holds a complete `ui` block with the setting on. `node scripts/genui-upstream-report.mjs
--upstream <checkout>` reports whether upstream has moved and which vendored files changed.

The spec language cannot run code: the parser and evaluator contain no `eval`, `Function`,
`innerHTML` or `dangerouslySetInnerHTML`; every value is text drawn by React Native components (a
spec's markup is shown as text), and an `OpenUrl` or link needs `http://` or `https://`. So a `ui` block
is drawn in the office's own React tree, not in the frame an `app` block gets.

**Graphics** (Settings → the scene picker, per device) is Auto, Low, Medium or High. Auto picks for
the device and steps down when frames keep coming late; Low draws no shadows and no post effects at
30 frames a second.

**Sticky notes** (Settings, host-wide) are the owner's notes on the 3D whiteboard: up to four,
60 characters each, typed with `;` between them. While there are any, the whiteboard lists five
agents instead of ten and the notes take its right half.

## The host

While an office surface is open, the `office.machine` subscription sends a reading every 10 s:
memory (the daemon's cgroup when it has a cap, else the host's), CPU, and for each agent the
memory, the process count and the TCP ports of the processes that carry its `PASEO_AGENT_ID`. The
Host entry in the Attention tab shows the memory in use and opens a card with the agents by memory.
On a Mac (`server/machine/macos.ts`) the same reading comes from the system's commands, run without
a shell and with a timeout: `sysctl -n hw.memsize hw.ncpu vm.loadavg vm.swapusage`, `vm_stat`, `top -l 2`
for the CPU, `ps -axo pid=,rss=,comm=` for the largest processes and `df -k` for the home disk. Memory in
use is what Activity Monitor calls Memory Used: the anonymous pages less the purgeable ones, plus the
wired pages, plus the pages the compressor occupies, times the page size `vm_stat` names in its first
line (4096 on an Intel Mac, 16384 on Apple Silicon); the file cache is not counted.

A Mac does not let a process read another's environment, but `ps -axEww -o pid=,ppid=,rss=,command=`
prints the environment after the arguments of the user's own processes, and the daemon and its
agents run as one user. One call reads every process; a row counts for an agent when its **last**
`PASEO_AGENT_ID=` token (the environment follows the arguments, so an argument that says the text
comes before it) is an id of an agent the daemon has with a runtime, and its parents are genuine: the
parent is a counted process of the same agent, since a child inherits the environment, or the
process is the top of the chain, started by the daemon or left behind with launchd (pid 1). A
command line that only contains the text sits under a shell or another program that carries no id,
so it is dropped; the daemon and its ancestors are never counted. A decoy would have to be started by the daemon or by launchd itself to be counted, and it would
only add its memory to that agent's figure. A process that cleared its environment is not found. Linux needs none of this
(`/proc/<pid>/environ` is the process's own). The rows feed the same `buildMachine`, so memory by
agent, process counts and "left running" appear, with `perAgent: true`. The ports come from
`lsof -nP -iTCP -sTCP:LISTEN -Fpn`, which lists the user's own processes by pid; if it fails, no
port is shown and no idle agent is marked as left running for lack of one. Environments and
arguments are never shown or stored; the name stays the program's `comm`. If `ps -E` shows no
environment at all (the flag unsupported or everything hidden, judged by `PATH=`, `HOME=` or
`USER=` on any row), the reading says so (`perAgent: false`) and lists no agent, and the Agents
section explains why instead of "Memory by agent". Only live agents are counted, so what a closed
agent left behind is not listed on a Mac. Clean-up is still refused on a Mac, so no process is
ever signalled there (`canCloseRuntime: false`): it waits until the readings have been seen on a
Mac. The readings were built from the commands' documented output (see `docs/verified.md`).

In **Host → This instance → Details**, inspect system swap, disk space on the home filesystem, load averages and the largest process groups by resident memory. RAM and CPU history covers up to 30 minutes of Office readings. With **Keep watching** on, the
host is read every minute with no office open, so that history has no gap, and memory at 90% goes
to the webhook. The same view lists workspace services, agent listening ports, workspaces with changed lines and measured npm and pip cache sizes. **Refresh** takes another snapshot.

### Plan limits

The Host card is in four sections: Overview (memory, CPU, the closest plan limit and what was
left running), Plan, Agents (memory by agent, models and forgotten work) and System. Plan lists
each provider's plan limits (the 5 hours, the week, whatever the provider reports) with how much
is used and when it resets, and a switch to count the provider. A provider switched off stays
listed there and is left out everywhere else: the toolbar's button, the closest limit and the 3D
floor. A plan nobody pays for reads as used up, so switch that one off (`planHidden` in the host
settings, shared by every device). The office asks Paseo for them
(`office.plan.usage.request`, which reads `providers.listUsage()`) when it opens and every two
minutes after; it stores none of it. With **Keep watching** on, the server reads them too, every
5 minutes, to tell the webhook as they pass 80%, 95% and 100%; that reading is also the only one
the backlog's auto-start gate trusts (see Boards and wakes). A provider that is unavailable or reports no percentage is not
listed, and a host whose Paseo has no provider usage shows no limits at all.

From 80% used the Host button in the toolbar names the closest limit instead of the memory, in the
warning colour; from 95% in the danger colour; at 100% it reads "Out of Claude" (or the provider's
name). When a limit's use rose between two readings at least 5 minutes apart, and at that rate it
reaches 100% before its reset, the toolbar shows "Claude 5 hours: at this pace out by Thu 14:00"
(the provider, the window, the weekday and the 24-hour time in the device's locale and zone) for
the soonest such limit of the counted providers, whatever the limits' level: with no limit at 80%
yet it is the whole note, in the warning colour; otherwise it follows the note after " · ". The page
keeps each limit's earlier reading for this and replaces it only by one at least 5 minutes later,
so the pace shows after the second reading 5 minutes on and is worked out again every 5 to 7
minutes. The kept readings are dropped when the office closes, so a pace needs two fresh ones. It
is a line, not a rule of the gate, and a limit already out has none. On the 3D floor a plan at 100% puts the countdown board on the wall, and the people on that
plan who are resting take a break in the pantry until it resets. Whoever is still working keeps
working.

The host setting `handOverWhenOut` (off at first) has the office hand tasks over by itself (see
Boards and wakes): when the plan watch finds a provider's closest limit at 100%, every lobby task
held by an agent of that provider that is not running or starting is handed over, its note saying
"Where Builder left it (handed over when Claude ran out): ..." (or "… ran out). It needed: …" for
a blocked one). Duties and rooms' tasks are left alone. It happens once each time the limit
reaches 100%, and again only after the limit has fallen back (a reset) and risen again. Nothing is
handed over unless an agent the pickup could hand lobby work to (idle or at home, not an internal
or background session) runs on a provider whose limit is not at 100% too, since the task would
have nobody to go to. Whatever the setting, while the plan watch's last reading, no older than
15 minutes, has a provider at 100%, the pickup gives that provider's agents no unnamed lobby task
or duty; a task named for one of them still goes to it. It needs **Keep
watching**, which runs the plan watch and keeps the directory open: with it off nothing is handed
over by itself.

Local readings come from Linux (`/proc`) or macOS. On Windows the Host card is available when
Office finds a configured SSH-MCP installation.

**Host → SSH** shows the hosts provided by SSH-MCP. Select a host to see its readings in detail.
Load is the one-minute load average relative to the number of cores, so it can exceed 100%.
The disk gauge shows the fullest reported mount. Office reads these metrics while the SSH tab is
open. If Office finds no installed SSH-MCP configuration, the card shows the local reading on its own.

An agent has left something running when it has been idle for 30 minutes with a port open, or when
it is closed or archived and processes of it remain: the daemon collects an idle runtime after an
hour, and a dev server the agent started can outlive that. Clean up, for one agent or for all of
them, calls `office.machine.cleanup.request` (`server/machine/cleanup.ts`). On a host whose SDK has
an agent's `closeRuntime()`, an idle agent's runtime is closed, so its next prompt resumes it.
Stock Paseo 0.16 does not have it, so there the card offers clean-up only for what a closed agent
left behind. Whatever still carries the id of an agent without a runtime gets SIGTERM. An agent at
work is refused.

A process whose agent id this daemon does not know is never shown and never signalled, since a
second daemon on the host would see the first one's agents that way. The office's own process and
its ancestors (the daemon and what started it) are never signalled, and an agent id that chain
carries in its environment is refused: a daemon started from an agent's shell has that agent's id.

## The janitor

The office shows how full each agent's context is, from the `lastUsage` its provider reports. The
Janitor entry in the Attention tab counts the contexts that are 85% full or more, and its card
lists every agent, the fullest first, with two actions for an agent that is idle or stopped on an
error. Clean context sends the provider's `compact` command. Reset session sends its command for a
new conversation, the first of `clear`, `new` and `reset` that the session lists, after a second
press: the plugin kit has no confirm dialog. Both go as a prompt through `office.janitor.request`.
An agent at work is refused, since the command would cut its turn, and a provider without the
command says so under the buttons. A provider reports a context's size when a turn ends, so after a
reset the old number would stay until the next turn; the office reads a reset agent's context as
empty until the provider reports another number (`settleResets` in `server/directory.ts`). The janitor
reads no process, so it is the same on a Mac; it is the host's clean-up of what an agent left
running, in the Host card, that a Mac does not offer yet.

## The stand-up

The Stand-up entry in the Attention tab reports every room with an agent in it: its branch, its
ticket, its pull request, what blocks it, and what each agent is at, with the agent's newest note on
the room's board from the last 24 hours. The office calls no tracker and no forge for it and holds
no token. The ticket is the workspace's metadata keys `tasks.key` (the ticket's key) and `tasks.url`
(its link), which any plugin or script may write; without `tasks.key` the report has no ticket. The
branch and the pull request, with its checks, its review decision and whether it conflicts, are on
the workspace descriptor the daemon keeps current for the sidebar (`projectWorkspace` in
`server/directory.ts`). A blocker is an agent that waits for your answer or stopped on an error, or
a pull request with failing checks, requested changes or conflicts.

"Ask for an update" posts one note per idle agent on its room's board, each naming its agent.
The agent answers with `office_post`, and its note shows in the
report. An agent is asked once per opening of the card, and the button is off while "Wake agents"
is off. "Copy as text" copies the report.

## The stand-up notes

The office also writes the day's entry in a folder of stand-up notes, one `daily-standup-YYYYMM.md`
per month. Nothing runs until you set "Notes folder", an absolute path. "Time zone" is the notes'
zone, the host's when empty. "Stand-up days" are the days of the 8:00 run, a row of seven buttons,
Monday to Friday by default. A host that had the office's settings before the days were a setting
keeps Sunday to Thursday. With no day chosen nothing runs at 8:00, and the bell still starts the
notes.

Each run, and each click on the 3D floor's bell, starts an agent titled "Stand-up notes" in the
notes folder's workspace, unattended: the first enabled, ready provider in the daemon's order, with
that provider's default model, in its mode that edits files without asking (Claude's "Accept File
Edits") or else its default mode. That mode covers file edits; whether the writer's shell commands,
such as `git log`, ask first is up to the provider's own settings. Whatever asks, the writer waits
on the permission until someone answers it. The writer gets the stand-up report as text and is told
to write the day's entry in that month's file, directly in the notes folder, creating the file if
needed, and to edit nothing else and commit nothing. It follows the stand-up notes instructions for
the folder, which may sit in the folder's own `AGENTS.md` or `CLAUDE.md` or in a parent folder's;
only when there are none does it write a `## DD Month YYYY` header and a short note of what was
done, what blocks it and what comes next. Either way the entry's header line is `## DD Month YYYY`,
which is how the office finds it, and an entry already there is brought up to date in place.

One writer runs at a time, and the office keeps it in `<PASEO_HOME>/office/notes-writer.json`, so a
restart does not start a second. An entry counts as written only when its `## DD Month YYYY` header
starts a line of the month's file after the writer's turn; the office then records the time and
archives the writer. A writer that fails, is stopped or closed, or ends without the entry is left as
it is and stays named, with an "Open the writer" button that opens its session in the office's
column, on the Stand-up card and the notes card; while it is at
its turn again, no new writer starts. "Stand-up notes" under the Stand-up card's line opens the
notes reader at the month’s newest entry. Select a date to read that entry, or use the month arrows to browse earlier files. The entry strip also includes the file’s introduction and Contents when present. Contents links open their entries. The
server reads only `daily-standup-YYYYMM.md` directly in the notes folder.

"Writer mode" in the settings is the mode the writer starts in. Its pills are the modes of the
provider the writer runs on, by the provider's own names, less the one that only plans: for Claude
Always Ask, Accept File Edits, Auto mode and Bypass; for Codex Default Permissions, Auto-review and
Full Access. "Office's choice" is no mode set: the writer accepts file edits where its provider
offers that, else takes the provider's default. Accepting edits approves edits only, so a writer
that calls another tool or a command then waits for an answer nobody gives at 8:00 and leaves no
entry; a mode that asks for less lets it finish. A mode that asks for nothing (Bypass, Full Access)
runs any tool or command unattended, and the row says so. A stored mode the provider does not
offer falls back to the office's choice, and the row says which mode is used. The mode holds from
the next run.

## Schedules

The office runs four schedules of its own (`server/local-schedules.ts`): the stand-up notes at 08:00
on the "Stand-up days" in the notes' zone, while a notes folder and a day are set, the duty board
at 08:00 every day in the same zone and at each later time a listed duty has (one schedule of
several times, set again when the list is saved), the incidents check every 5 minutes, while a tracker is on, and the intake every 10 minutes, while a source is set up (see Intake). They are timers in the plugin's process,
not Paseo schedules, so they are not in the app, `paseo schedule ls` or `list_schedules`. The
office sets them from its settings each time it starts and at each save, and stores nothing.

- A run that came due while the daemon was down is not made up, with one exception: the stand-up
  notes. When the office starts, or a save sets its notes schedule (a new folder, zone or days),
  and today is a stand-up day in the notes' zone, 08:00 has passed there and today's
  `## DD Month YYYY` entry is not in the notes, the day's run is made up at once, and waits for the
  Paseo API like any run. It starts nothing while a writer is at work, so a day never has two
  entries, and it follows the rule below when it could only start on a later day.
- After a daemon restart, a run waits until the office is opened or an agent opens or ends a turn.
  An installed plugin gets the Paseo API only on a handler's or a hook's context, and a run needs
  it. The plugin's log says when a run is waiting.
- A notes run that could only start on a later day than it was due is dropped, so no entry is
  written for the wrong day.
- The duty board's run needs no Paseo API: it posts at once, and only handing a duty to an idle
  agent waits for the API. When the office starts, today's duties not yet posted whose time has
  passed are posted; an earlier day's are not. A run at a later time posts the duties whose time it
  is; the duties of earlier days leave at the 08:00 run. A run that fires late but before the next
  08:00 (a 23:59 run at 00:01, or after the host slept) still posts its duties on their day; one
  that fires after the next 08:00 is not made up. Nor is a late-time run that came due while the
  daemon was down once midnight has passed: before 08:00 the start posts nothing.

## Incidents

The office rings my-office's incident alarm for a new Jira bug, a new Sentry issue, a CloudWatch
alarm or error lines in a CloudWatch log group. "Jira projects"
takes project keys, and a new issue in one of them rings when its type is one of "Jira issue
types" (names, comma separated; Bug when empty). "Sentry organisation",
"Sentry projects" and "Sentry address" (`https://sentry.io` by default) do the same for a new
unresolved Sentry issue. Jira's search answers a project key it does not know with nothing, so each
check first asks Jira for the projects by key: a mistyped key, or one the token's user cannot
see, is a problem on the Incidents card.

Each tracker needs a sign-in, set under Services in the office's settings. Jira takes its
address, the account's email and an API token; Sentry takes an auth token. "Save connection"
writes them to `office/trackers.json` in Paseo's home on the host, a file only the daemon's user
can read (mode 600). The tokens are stored there as typed, not encrypted. A saved token is never
sent back to the app: its field stays empty, and the settings say only where the sign-in comes
from. "Test connection" sends one signed-in request with what is typed and saves nothing; a
Sentry test asks the organisation and address already set. "Remove" deletes a saved connection.
A save holds from the next check, with no daemon restart.

A host with no saved connection reads `ATLASSIAN_BASE_URL`, `ATLASSIAN_EMAIL` and
`ATLASSIAN_API_TOKEN`, and `SENTRY_AUTH_TOKEN`, from the daemon's environment, as before. A saved
connection comes first, and a changed variable takes a daemon restart.

CloudWatch needs no token in the office. "AWS profile" names a profile of the `aws` CLI on the
host and "AWS region" the region; with both set, each check runs
`aws cloudwatch describe-alarms --state-value ALARM` through that profile, and an alarm rings each
time it goes into ALARM. "CloudWatch log groups" takes up to 10 log group names, and "Error
pattern" a CloudWatch Logs filter pattern (`ERROR` by default): lines that match ring once an hour
for each group, as "12 error lines in /aws/lambda/pay". The office counts the lines and never
copies one, since a log line can hold a customer's data; the incident opens the log group in the
AWS console. The profile needs `cloudwatch:DescribeAlarms` and `logs:FilterLogEvents` only, and
the office writes nothing to AWS. The CLI is looked for on the daemon's PATH and in
`~/.local/bin`. When an SSO sign-in runs out, the Incidents card and the profile's field say to
run `aws sso login --profile <name>` on the host, and the next check after that works again.

The first check records what exists and rings nothing: an alarm already in ALARM when CloudWatch
is turned on is not rung. Each check reads from the last successful
one less 10 minutes, because Jira compares `created` to the minute; the office writes the time in
the token user's profile zone, read from `/myself` each check. A check opens at most 20 incidents
per tracker, the oldest first, leaving the rest to the next check. The office keeps each tracker's
last check, the keys it saw in the last 2 days and the open incidents in
`<PASEO_HOME>/office/incidents.json`; without that file the next check is a first check again.

An incident stays open on the host until it is dismissed, a day old, or resolved in its tracker,
so whoever opens the office later still gets the alarm. Each check asks Jira which of its open
incidents are in a done status and Sentry for the status of each (20 at most a check), and closes
those; a CloudWatch incident closes only by Dismiss or its age. A failed
check keeps the Attention entry and a problem line on the Incidents card until a check succeeds or
the tracker is turned off. A tracker turned off and on again starts afresh: its first check after
rings nothing for the time it was off.

Each incident on the card has a link to its page, **Analyze**, **Add to lobby** and Dismiss.
Analyze opens the New agent form with the incident as its first prompt (the tracker, the key, the
title and the address, and a line asking for the likely cause and a proposed fix, with nothing
changed until it is agreed): choose the workspace and press Create. Add to lobby posts the same
text as a task on the lobby's board, where an idle agent picks it up as it does any to-do; while a
task with the incident's address is on that board and not done, the row says "On the lobby board"
and offers no second one.

The Incidents card dismisses through `office.incidents.dismiss.request`. The 3D floor shows a
banner naming the newest, with 25 s of red light, a fail bubble over each person at work and
my-office's siren for one this device has not rung for. A device keeps what it rang for in its
`office-device` setting, so opening the office again rings nothing. The siren plays only while
Sound is on, and only after a press in the scene.

## Intake

The office can post tickets from Jira, and issues from GitHub (see GitHub below), as lobby tasks
by itself. **Jira intake** in the host
settings (`jiraIntakeJql`) takes a JQL of the owner's own, up to 1,000 characters; while it is
empty, or Jira has no sign-in (the one under Services, or the daemon's environment, as for
Incidents), the intake is off and has no timer.

- **Where the settings are.** Settings, Services, **Intake**, after the connections. "Jira tickets
  to bring in (JQL)" is a field of three lines, up to 1,000 characters, saved when it loses focus,
  with the hint that the tickets it matches become lobby tasks, each once, and that imported
  tickets should be left out of it. "Imported tasks go to" is Backlog or To do (`intakeLands`).
  The switch "Let the gate start imported tasks" (`intakeAutoStart`) warns that a ticket's text
  reaches an agent without you reading it; "Comment the result on the ticket"
  (`intakeWriteBack`) warns that everyone who can read the ticket reads the comment. The intake
  uses the Jira connection above it and takes no token of its own.
- **The status line and Read now.** Under the fields: "Not set up: needs a JQL and the Jira
  connection." while the source is not set up; otherwise the last run, as "Last read 12:40: 3
  imported" or "Last read 12:40: nothing new" (the device's clock), or "Not read yet." before the
  first, then the run's problem in the warning colour, and "Waiting: 50 imported tasks are open."
  while the cap holds the intake back. **Read now** runs the intake at once
  (`office.intake.run.request`), shows "Reading..." meanwhile and a failure like any other
  button's, and is off while the source is not set up.
- **The chip.** A task from a ticket shows the ticket's key ("PROJ-12") on its meta line, on the
  kanban card, the list row and a room's copy alike. It is a link: it opens the ticket's address
  as the Reviews card opens a pull request, and its name for a screen reader is "Open PROJ-12 in
  Jira" (or "Open <key> on GitHub"). Only an http or https address is opened; any other is shown
  as plain text. A press on it changes nothing on the task.

- **What is read, and how often.** Every 10 minutes the office sends the JQL to Jira as written
  (`GET /rest/api/3/search/jql`, the office adds nothing to it) and reads the summary and the
  description, 20 tickets a page. Tickets already imported do not use up a run: it reads page after
  page until it has 20 it has not posted, or has read 5 pages (100 matches). When those 100 are all
  imported, the problem says "the first 100 matches are already imported: narrow the JQL", and
  nothing new arrives until the JQL leaves imported tickets out. So write a JQL that does: a label
  the team takes off (`labels = agent`), or a status the team moves tickets out of (`status = "To
Do"`). A run that comes due while one is still going is skipped. An answer over 5,000,000 bytes
  is refused ("Jira answered with too much data").
  `office.intake.run.request` runs it at once and answers the state, so the settings can test a
  JQL without waiting. The JQL is never written to the plugin's log, and neither is the token.
- **Where a ticket lands.** Each ticket becomes a lobby task posted as the user, for no agent and
  no team: `KEY summary`, the ticket's link on the next line, then a blank line and the
  description as plain text, cut to 1,000 characters with "…". The post keeps the ticket as its
  `source`. It is held in the **Backlog** unless `intakeLands` is `todo`; Backlog is the default so
  that the owner reads a ticket before an agent does. The auto-start gate leaves held imported
  tasks alone unless `intakeAutoStart` is on: with it on, a ticket is started without the owner
  reading it, so leave it off unless only people you trust can write tickets. An agent handed it reads `The office
assigned you lobby task p12 from Jira PROJ-12.`, and `office_read` shows the task as
  `p12 task open (backlog) [Jira PROJ-12], from the user: ...`. A reopen keeps the source.
- **Once only.** A ticket is posted once. Before posting, the office looks for a post with the
  same source on any board, done or not, then in `<PASEO_HOME>/office/intake.json`, which keeps
  the newest 5,000 tickets posted. The task is posted first and recorded after, so a crash between
  the two leaves it on the board, where the next run finds it. A task the owner deletes does not
  come back. A ticket moved to another project gets a new key, and is imported again under it. A
  seen file that cannot be read posts nothing until it can (the state says so):
  the office never imports on bad data. Deleting the file on purpose brings back every ticket the
  JQL still matches that is not on a board.
- **The cap.** With 50 imported tasks open or held (any source's, not done), a run posts nothing
  more and the state says it is waiting. Finish or delete some and the next run goes on.
- **Write back** (`intakeWriteBack`, off). When a task from a ticket becomes done with a result,
  the office comments on the ticket once: `Done in the office by <agent's title, or "the owner">:
<result>`, cut to 2,000 characters (`POST /rest/api/3/issue/<key>/comment`). The token must be
  allowed to comment; nothing else is written and no ticket is moved. A task done without a
  result, or while the switch is off, writes nothing. A failed comment is tried once more at the
  next run; after that its problem stays in the state and it is not tried again (after a daemon
  restart it may be tried twice more). A comment that timed out is not tried again, since Jira may
  have taken it; the state says "the comment may not have arrived". A task reopened and done again
  comments again. The comment is the task's result as its agent wrote it, and everyone who can read
  the ticket reads it: with write back on, a ticket's author can ask for something in the ticket's
  text and read the answer on the ticket.
- **The ticket's words are other people's.** Anyone who can write the ticket writes the task, and
  the task reaches an agent's prompt, which can lead the agent to run commands with its
  permissions. The office keeps the text in its place: the summary is one line of 300 characters
  at most (cut further when the key and link are long, and a ticket whose key and link alone
  would not fit in a post is skipped), control characters are removed from the description, the link is built from the saved
  Jira address and the key (never taken from Jira's answer), a ticket whose key is not a Jira key
  (`PROJ-12`) is skipped and counted ("1 ticket skipped: unreadable key"), and in the assignment
  the text is indented like any task's, so it cannot pass for the office's own lines. That is no
  defence against words that only ask: read a ticket in the Backlog before you start it.

### GitHub

GitHub issues come in the same way, from a second source. Two host settings set it up:
`githubIntakeRepos`, up to 10 repositories as `owner/repo` (none twice, whatever the case; neither
part may start with a dash, which keeps an entry from being read as an option), and
`githubIntakeSearch`, up to 200 characters, `label:agent is:open` at first, which may not start
with a dash or name a place (`repo:`, `org:` or `user:`: "the search cannot name a repository:
list it above"). With no repository the source is off and, with Jira off too, there is no timer. Under
Services, **Intake**, below the Jira field: "GitHub repositories to bring in from" (one per line;
the field names the line it will not take, for example `Line 2: "-evil/x" is not owner/repo`, and
saves nothing until every line is right) and "GitHub search" (one line), with the hint "Read with
the host's gh CLI and its sign-in. The office keeps no GitHub token." A status line for GitHub
follows Jira's ("GitHub: last read 12:40: 2 imported"), and **Read now** runs every source.

- **It uses the host's `gh`.** There is no token in the office and none is asked for: the office
  runs `gh` on the host (found on the daemon's PATH or in `~/.local/bin`, no shell, 30 seconds at
  most, 8 MB of output at most) and `gh` uses the account it is signed in with (`gh auth login`).
  Only github.com is read: GitHub Enterprise hosts are not supported. For each repository the
  office runs `gh issue list --repo <repo> --search <search> --limit 20 --json
number,title,body,url`, each value one argument, so neither a setting nor an issue's text can
  become an option. A repository that fails does not stop the others; the problems are joined in
  the state.
- **The key and the link.** An issue's key is `<repo>#<number>` with the repository as written in
  the settings, lower-cased (so editing a setting's case does not bring the issues again), and the
  number from `gh` (a positive integer, else the issue is skipped and counted), for example
  `acme/web#12`. An issue whose own `url` from `gh` is not `https://github.com/<repo>/issues/<number>`
  (compared without case) is skipped and counted too: GitHub's search could otherwise bring in
  another repository's issue. The link is built, `https://github.com/acme/web/issues/12`, never
  taken from `gh`'s output. The task reads `acme/web#12 title`, the link, a blank line and the body,
  cleaned and cut as Jira's are, and an agent handed it reads `The office assigned you lobby task
p12 from GitHub acme/web#12.`
- **Which issues, and how many.** A run reads the first 20 matches of each repository, with no
  paging, and posts those it has not posted (the same board check and the same seen file, as
  `github:<key>`). At most 20 are posted per source per run, and the cap of 50 open imported
  tasks is shared with Jira. So write a search that leaves imported issues out, for example
  `label:agent is:open -label:in-office`, with `in-office` a label the team adds once the issue is
  in the office; otherwise, once the first 20 matches are imported, nothing newer is reached, and the problem says
  so ("acme/web: the first 20 matches are already imported: narrow the search").
- **Problems**, each one short sentence and never the CLI's own words: "the gh CLI is not installed
  on the host", "gh is not signed in on the host", "acme/web: not found, or gh's account cannot
  read it", "acme/web: gh did not answer in 30 seconds", "acme/web: gh answered with something
  unexpected" and "acme/web: gh failed".
- **Write back** is the switch above. A done task from an issue is commented with `gh issue
comment <number> --repo <repo> --body <text>`, the same text and the same cut as Jira's, the text
  one argument after `--body` (a result that starts with `--` is still only the body). One attempt
  at done, one more at the next run, none after a timeout. `gh`'s account must be allowed to
  comment on the repository. A repository the owner removed from the settings is not commented on
  ("acme/web is no longer read: not commented"), and that task is not tried again. `gh` is run
  from the home directory with `GH_HOST=github.com` and no prompts, whatever the daemon's
  environment says.

The state for clients (`intake` in the office's state) has, for each of Jira and GitHub, whether it
is set up, the last run's problem (a short safe text, logged once each time it changes; Jira's own words are kept
apart from its status and left out of the log, since they can quote the JQL), when it last ran and how many tasks that run posted,
and whether the intake waits at the cap.

## Weather

Weather defaults to Off. Under Manual, choose Clear, Cloudy, Rain, Storm or Follow the season.
The seasonal sky is cloudy for Halloween and clear otherwise. Rain falls outside the room and
brings out the open umbrella, puddles and wet-floor sign at the entrance. The umbrella stand is
always there. Clouds dim the daylight, fog reduces visibility and storms flash. With sound on,
storms can play thunder. The app’s theme selects day or night. The window glass, people’s
behaviour, 2D floor and List keep their usual appearance and behaviour.

From a service uses an address supplied by the host. HTTPS is accepted, as is HTTP on loopback.
With an office open the host reads it at most every 15 minutes. It waits at most 10 seconds and
reads up to 64 KB. A redirect, malformed answer or failed request switches the sky to the
season’s weather and displays the problem under Weather address and in Attention until a read
succeeds. An empty address also follows the season. The host keeps a reading in memory for up to
30 minutes. Restarting clears it.

An Open-Meteo example for Berlin is
`https://api.open-meteo.com/v1/forecast?latitude=52.52&longitude=13.41&current=temperature_2m,weather_code,cloud_cover`.
Replace the latitude and longitude for your location. A static JSON file also works:

```json
{ "current": { "weather_code": 63, "temperature_2m": 14.2, "cloud_cover": 90 } }
```

The WMO code must be an integer from 0 to 99, and the temperature a number in degrees Celsius.
Numeric cloud cover is a percentage limited to 0–100. Without it the host estimates cloud cover
from the code. Other fields, including `current.is_day`, are ignored. Only the weather reading
reaches the scene. The address, including its query string, is visible in the host settings.

## Reviews

The Reviews entry is in the Attention tab while a workspace has an open or draft pull request. Its
card is a queue: what waits for a review first, then what was sent back, the approved and the
drafts, each with its branch, its base, the size of the checkout's changes, its checks and its
conflicts, from the same descriptor as the stand-up. No SDK call fetches a diff or submits a
verdict. **Open workspace** opens the workbench over the office to show the diff. The pull request link opens its forge.

"Ask for a review" posts a note to the team's newest idle agent. The note's first line starts with
`Review request:` and its second is the pull request's address; that is how the office finds the
request again, and the asked agent's first note after it is shown as the review
(`client/review-text.ts`). While a request has no answer and its agent is still in the room, nobody
else is asked.

## QA

The QA entry is in the Attention tab while a workspace has a pull request with checks, an agent at a
test run, or a script. Its card lists, team by team, the checks that fail or run, each with a link
to its run on the forge, the agents' test runs, and the workspace's scripts and services. The office
carries at most 40 checks of a pull request, the failing and the running first.

"Show log" reads the end of a script's output through `office.script.log.request`. A caller names a
workspace and a script, never a terminal: the server finds the script's terminal in its own
directory. It captures the terminal's last 400 rows, because the last rows of a terminal are the
empty end of its screen, and answers with the newest 40 lines that have something on them, each cut
at 400 characters (`server/script-log.ts`). Nothing of a log is kept, and no agent tool reads one. A
check's own log stays on the forge: no SDK call fetches it.

## The library

The Library card lists each workspace's skills from its `.claude/skills`, `.agents/skills` and
`.codex/skills`, and the host's from the Claude config folder's `skills/`, `~/.agents/skills` and
`~/.codex/skills`. They are read through `office.skills.request` each time the card opens; the
server reads only those folders and finds a workspace's folder through the SDK, so a client sends
no path (`server/skills.ts`). The Library entry is in the Attention tab while the office has a team.
On the 3D floor the library's chip and its bookshelf open the same card, also in an office without
a team, where it lists the host's skills. An agent whose step opens a skill (Claude Code's `Skill`
tool), reads or writes a `SKILL.md`, or runs a command that names one goes to the library.

"Teach a skill" posts a note to an idle agent of the team, as a review request does: its first line
starts with `Skill request:` and names what the skill teaches, and the agent writes the skill into
the workspace, where it is in the changes to review. The office installs and removes no skill.

## Data

The office keeps its files in `<PASEO_HOME>/office/`: `boards.json`, `duties.json`, `chat.json`,
`notes-writer.json`, `incidents.json`, `tenure.json` (the team ledger), `lift.json` (the build last serviced) and
`auto-start.json` (`{ version: 1, day, count }`: the backlog tasks the office started by itself that day) and
`intake.json` (`{ version: 1, seen }`: the tickets the intake posted, see Intake), and
`telegram.json` and `telegram-state.json` (the bot's token and where its poll has got to, see
Telegram). Its settings are Paseo settings documents
(`shared/settings.ts`): `office` for the host, and `office-device` and `office-column` for each
device. The host's are in `<PASEO_HOME>/plugin-settings/office/office.json`; an earlier version of
the plugin refuses a document a newer one has saved, and removing the plugin deletes it.
With **Undo last turn** on, the office also writes git objects (blobs and trees, no ref) into the
repositories agents work in, and a temporary index in the system's temporary folder while it
does; nothing else of it is kept on disk, and the checkpoints (ten turns an agent) are only in
memory.
A save of a device setting spreads the values it read and never passes a key with no value: the host
refuses a document that holds `undefined`, and the device then keeps nothing.

## Staff and daily life

The indoor scenes cover packed lunches at the microwave, the duty board, tea, the accountant, rounds,
HR, farewells, interns, reception and delivery staff, the altar, lift servicing, the post and the
quarterly fire drill. They run on the office clock. During the 12:30–13:30 desk nap, the lively
floor pauses new activities. Street outings are separate.

The accountant reads provider-reported spending. HR uses the repository’s first commit month for
birthdays. The tenure ledger identifies each team by the name it goes by. A team that
takes another name, the office's own or its workspace's in Paseo, keeps its record while the
office runs; a workspace renamed in Paseo while the office is not loaded starts a new record and
the previous name goes quiet. The first set of workspaces is permanent. A later team
can graduate after 20 turns over

## The street

Open **Outdoor scene** in Office settings. Select **City**, **Countryside**, **Beach** or **Plain**. **Lighting** offers **App theme**, **Day** and **Night**. Countryside with Day lighting gives the green landscape shown in my-office. Choosing a different environment rebuilds the floor; changing the lighting keeps the camera. Each device remembers its choices. Older devices retain their saved street preference as City or Plain. The city supports taking the lift to the pavement in Walk mode.

The device requests the CC0 car models from `office.world.street` and passes the string to the isolated scene in the `street.kit` start option. A failed request leaves procedural traffic and shops available and shows a floor note. The day’s street activities include shopping trips, the guard, lunch, evening drinks, the photo studio and pickleball. The upstream chain modules and branded artwork are excluded. Plain canvas signs carry the names from `scripts/street-brands.mjs`. See the street section of [the source inventory](../vendor/SOURCES.md) when importing upstream changes.

A seated agent carries its workspace pull request’s completed check status into the street. A failed check makes the pickleball day red, and a successful check supplies green. Pending or unavailable results supply neither. While a street is open, the host checks local Git tags in occupied workspace folders once a minute. Newly observed tags queue a photo booth visit. Existing tags establish the opening baseline. The host also reads `claude --version` every five minutes when the CLI is available. An observed version increase triggers the handset outing.
